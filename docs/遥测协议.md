# 遥测协议

> 固件 ⇄ 上位机（`tools/`）之间的数据约定。**改协议要两边同时改，且需双方确认。**
> 最后更新：**2026-10-01** · v1.4（state 增加 5=起步找线；同步无线链路节拍与“每帧=10ms 增量”约定）
> 帧格式**未变** —— 没有新增/删除/换序任何字段，旧解析脚本不受影响。

## 一、物理层

| 项 | 约定 |
|---|---|
| 接口 | USART1（PA9 = TX，PA10 = RX），接 USB-TTL |
| 参数 | 115200 8N1（数据量大了再升 460800；升之前两台机器都要改） |
| 速率 | `$T` 帧 100 Hz（板载）；**BLE 上：分频 2 ⇒ 50 fps**（2026-10-01 由 33→50，实测送达 44.8 fps）；`$U` 帧：主循环每 **100ms 一颗、左右轮流**（每颗 5 Hz、帧 4 Hz；**BLE 上 4 Hz 限流**，实测送达 3.3 Hz；`AUTO` 可关）；`$P` 上电一次；`$E` 事件触发 |
| 方向 | 车 → 电脑：`$T` / `$P` / `$E` / `$U`（后两者 2026-10-01 起也走 BLE，4Hz）；电脑 → 车：命令文本行 |

> **帧间隔约定（重要，改固件分频时必须知道）**：控制环固定 **100Hz** ⇒ **帧间隔 = 10ms × BLE 发送分频**。
> 工具不再写死这个值 ✗（本项目在“写死常量”上栽过多次），而是 `shared_log.frame_timing()` 从日志的
> `ms` 列推出来：分频 3 ⇒ ×3/30ms、分频 2 ⇒ ×2/20ms、板载快照 ⇒ ×1/10ms ✓
> （历史包袱：2026-10-01 之前的日志 `ms` 是“帧号×40”的合成值，`frame_timing()` 会特判 40ms ⇒ 仍按 ×3 处理 ✓）

## 二、帧格式

**通用规则**：ASCII、每帧一行、以 `\r\n` 结尾、逗号分隔、以 `$` + 类型字母开头。

### 2.1 `$T` 遥测帧（100 Hz）

```
$T,<ms>,<s0>,<s1>,<s2>,<s3>,<s4>,<s5>,<s6>,<s7>,<err>,<pwm_l>,<pwm_r>,<state>
```

| 字段 | 含义 | 类型/范围 |
|---|---|---|
| ms | 上电毫秒数 | 整数 |
| s0..s7 | 八路灰度二值化结果（**0=白，1=黑** —— 与模块原始极性相反，由 `app_trace.c` 归一化） | 0/1 |
| err | 循迹偏差（传感器编号单位，0 = 正中） | 一位小数，约 −8.0~+8.0 |
| pwm_l / pwm_r | 左右轮 PWM 占空比 | 整数，−100~100（负=反转） |
| state | 状态机 | 0=待机/丢线 1=循迹 2=避障 3=回线 4=精停 5=**起步找线** 6=**丢线找线**（5/6 均 2026-10-01 新增；2~3 为 A02 预留）|

> ⚠️ **`pwm_l/r` 是「算法打算给的值」，不等于电机实际得到的值。**
> 发车开关关着（`TRACE 0`）时电机不动，但 `$T` 照样报算法算出来的数 ——
> 这是**有意的**：可以上车前先在电脑上干看一遍算法输出对不对。

### 2.2 `$P` 参数帧（上电 1 次；`SET` 成功后也发一次）

```
$P,<ms>,<kp>,<ki>,<kd>,<base_speed>
```

> 作用：参数快照。**在线调参不会进 git**，靠这一帧把"当时用的是哪套参数"记进日志。

### 2.3 `$E` 事件帧（事件发生时）
```
$E,<ms>,<code>,<note>
```

| code | 含义 | code | 含义 |
|---|---|---|---|
| 1 | 丢线 | 90 | PONG（应答测试） |
| 2 | 检测到障碍 | 91 | 参数已修改 |
| 3 | 开始绕行 | 98 | 演示事件 |
| 4 | 回到循迹线 | 99 | 未知命令 / 其他 |
| 5 | 通过赛段标识 | | |
| 6 | 到达终点 / 开始精停 | | |

`note`：不含空格的短标签（便于人眼扫日志）。

### 2.4 `$U` 超声波帧（主循环每 100ms 一颗、左右轮流 ⇒ 每颗 5 Hz、帧约 10 Hz）

> ⭐ **2026-10-01 起：`$U` 与 `$E` 也走蓝牙了**（此前只走串口 ✗，导致“避障只能在插线时调”✗）
> - 频率：测量 **100ms 一颗**（每颗 5 Hz）；**BLE 上 4 Hz 限流**（250ms 一条，≈100 B/s）
> - 实测（2026-10-01，12~15 秒样本）：`$T` 送达 **43~45 fps**、`$U` 送达 **3.1~3.3 Hz** ✓
> - 形式：**纯文本行**，与串口完全一致 ⇒ 接收端靠 `AA 55 AA 55` 重新对齐（ASCII 不可能产生 0xAA，安全 ✓）
> - 固件：`app_log.c` 的 `Log_BleUsFrame()` / `Log_BleEvent()`；调用点：`main.c` 的自动测量块 + `Tlm_SendEvent()`
> - 工具：`btlog.DeFramer` 会先把文本行抽出来（`$T` 帧不受影响 ✓）；btview 有**超声波俯视图**
> - ⚠️ 负值语义：`-2` = 没回波（=前方空旷，**不是故障** ✓）；`-1` = 真故障（查线）；
>   **`-6`/`-3` = 驱动拦下重复触发（不是“没测到”）** ⇒ 显示端应保留上一个值，不要当成无数据
> - 命令 `US` 也会立即推一条到蓝牙 ✓

```
$U,<ms>,<l_mm>,<r_mm>
```

| 字段 | 含义 | 类型/范围 |
|---|---|---|
| ms | 上电毫秒数 | 整数 |
| l_mm / r_mm | 左（PA4/PA5）/ 右（PA1/PB5）距离 | 整数，单位 mm；**−1 = 无回波（真故障），−2 = 前方空旷/超量程** |

> 为什么要这个帧：超声波是避障的唯一输入，测量值必须能和其它量一起落盘/画图。
> 节拍由驱动层保障：**两颗不能同时触发**（轮流）+ 同一颗两次间隔 ≥60ms + 失败后 600ms 恢复期。
> **实测**：250ms 一颗（左右各 2Hz）成功率 100%；曾试 100ms 一颗，左侧掉到 42% —— 所以默认是 250ms。
> **兼容性**：这是**新增帧类型**，没有改动 `$T/$P/$E` 的任何字段（符合 §四 扩展规则）。


## 三、命令（电脑 → 车）

每行一条，`\r\n` 结尾：

| 命令 | 作用 | 回复 |
|---|---|---|
| `PING` | 连通性测试 | `$E,<ms>,90,PONG` |
| `GET` | 读当前参数 | `$P` 帧 |
| `SET <名字> <值>` | 改参数（如 `SET kp 1.35`） | `$P` 帧（改后的值） |
| `US` | 立即测一轮超声波（左→隔 60ms→右） | `$U` 帧 |
| `TRACE 0\|1` | **循迹算法发车开关**（0 = 只算不发，1 = 真的驱动电机）| `# TRACE drive=N` |
| `AVOID 0\|1` | **避障算法发车开关**（同上）| `# AVOID drive=N` |

可调参数名：`kp` `ki` `kd` `base_speed`。

> **完整命令表**（含各驱动的 bring-up 自检命令，共 20+ 条）见 `firmware/驱动接口说明.md` §六；
> 本节只列**与本协议帧直接相关**的命令。
>
> ⚠️ **算法发车开关出厂默认 0（只算不发）** —— 这是安全设计：烧录后车不会自己窜出去。
> 要真发车必须显式发 `TRACE 1`，且**开之前先把轮子架空**。

## 四、扩展规则

1. **新增字段只能加在行尾**——旧的解析脚本不会因此报错
2. **改字段顺序 / 删字段 = 破坏性变更**，必须双方确认（A01、A02 的代码都按本表写）
3. 上位机解析见 `tools/telemetry.py`，画图见 `tools/plot.py`
