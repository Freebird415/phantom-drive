# 文档维护规范

> 更新项目文档时读本文件。
>
> 最后更新：**2026-10-10**（新增 **§文档效率：一处定义·多处指路**（含唯一出处表）与 **§留言板规范**；目录纪律同步“结构 v2”：`工具箱.bat`、工作区 `agent对接.md`、`firmware/{文档,测试,算法快照}`）

## 0. 铁律：**不确定的事，不许写成确定的事**

> 这份仓库是**给多个 AI + 多个人共读**的。一句写得太满的结论，会被下游 AI 当成事实继续传播，
> 最后没人知道它其实只是**推测** ⇒ 越改越错还没人发现。

| 场合 | 写法 |
|---|---|
| **代码事实 / 协议约定 / 实测读数**（可复现、有出处）| 可以写肯定 = 是 / 等于 / 显示 |
| **故障真因的推断** | ❌"真因是 X" ⇒ ✅"**证据指向 X**（附证据：日志/寄存器读数/复现步骤）；**不排除** Y、Z" |
| **物理/机械的解释**（打滑、丢脉冲、零偏、装配误差…）| ❌"说明是打滑" ⇒ ✅"**疑为**打滑；也可能是轮距取值不对 / 编码器丢脉冲 / 陀螺零偏，**尚未分辨**" |
| **标定值 / 尺度 / 估算**（如 mm/计数）| 必须标：**名义值（推定）** + 依赖的假设 + 已知误差量级 + "未精标" |
| **单次实测的结论** | 标样本量："**单次**实测（1 趟）"，不要写成"稳定/总是/已经没问题" |
| **目测 / 记忆 / 转述**（如"跑道大约 10m"）| 标"**目测**/**转述**，未核实" |

**用法**：写结论时先问一句"**这个我能复现吗？**"——不能复现的，一律降级为"推定/疑似/待验证"。
看到别人（或别的 AI）写了过满的结论，**顺手降级**，并在 `项目记录/经验与踩坑.md` 留一条为什么。

## 文档效率：一处定义、多处指路

> 目标：**用最少的阅读量掌握信息**。谁要干一件事，读**一份**就该能动手；要细节时**最多再跳一次**。
> （这套规则既约束人，也约束 AI —— 绕弯的引用会白烧 token 和算力。）

### 三条规则

1. **一处定义，多处指路**：同一件事只在唯一出处写全，别处只写**指针** ＋ **执行必需的最小摘录（≤1 行）**。
2. **入口文档必须自足**：给"要干某件事的人"的文档，**步骤不能指向别处**（细节可以）。
   例：`项目记录/比赛日操作卡.md` 要能照着发车；`firmware/agent对接.md` 要能照着改代码；`tools/README.md` 要能照着跑工具。
3. **不许绕弯、不许嵌套引**：指针只能"由粗到细"（总纲 → 领域 → 细节），**最多跳一次**；不得 A→B→C 接力，更不得两个文档互指。
   发现"要翻第 3 份文档才能动手" ⇒ 说明前一份没写全，**回去补**，别再加一层引用。

### 唯一出处表（写文档 / 找信息前先扫一眼）

| 事实类型 | 唯一出处 | 别处怎么写 |
|---|---|---|
| 技术红线（尺寸·电源·固件体积·浮点·发车开关·代码缝）| `docs/技术约定.md` | 指针 +（必要时）1 行摘录，**不反向引** |
| 引脚与电气契约 | `docs/引脚分配表.md`（人）＋ `hardware/电气设计/netlist.json`（机）| 接线图/接线表由脚本从 netlist 生成，`自检.py` 校验 |
| 遥测帧格式与字段含义 | `docs/遥测协议.md` | 命令/接口细节 → 驱动接口说明 |
| 固件分层、接口、命令总表、调用骨架 | `firmware/文档/驱动接口说明.md`（权威＝各 `drv_*.h` 头注释）| 别处只列"最常用的几条"＋指针 |
| **A01/A02 文件边界 + 固件层硬限制 + 当前 Flash/RAM 余量** | `firmware/agent对接.md` | 别处只写"边界与硬限制见 …" |
| **现场**操作（发车 / 终点 / 合规红线）| `项目记录/比赛日操作卡.md` | 该文档**必须自足**，其他文档指向它 |
| 谁·什么时候·交什么 | `计划和任务/任务清单.md`（生成物）｜冲突以 `项目记录/开发记录.md` §3 为准 | 只引不抄 |
| 方案 / 分工 / 正向进度 | `项目记录/开发记录.md` | 只引不抄 |
| 实际做到哪、卡在哪 | `项目记录/实际进度.md` | 只引不抄 |
| 踩坑 / 试错 / 背景 | `项目记录/经验与踩坑.md` | — |
| 已拍板 / 已冻结事项 | `项目记录/决策登记.md` | 动手前扫一遍 |
| 日志怎么拿 / 怎么读 | `logs/README.md`（数据侧）＋ `tools/README.md`（工具侧）| 字段含义 → `docs/遥测协议.md` §六 |
| 文档与留言板规矩 | `docs/文档维护.md`（本文件）| — |
| 整理检查清单 | `docs/项目整理.md` | — |

> **只有三类"重复"是允许的**：① **现场/离线**要用的（比赛日操作卡能在没网没文档时照着做）；
> ② 有**脚本自动校验**的（引脚 ↔ netlist，由 `自检.py` 守）；③ 有明确"以谁为准"的**对外分发版**（任务清单 md/pdf）。
> 除此之外，看到同一段话出现两次 ⇒ 删掉一处、留指针。

## 项目记录三个文件 + 对外清单 的分工

| 文件 | 定位 | 内容标准 |
|---|---|---|
| `项目记录/开发记录.md` | 正向流程（纯净） | 只写"现在应该怎么做"：方案、分工、接口、物料、进度、里程碑；不写试错与返工过程 |
| `项目记录/经验与踩坑.md` | 全量记录（不降噪） | 踩坑、试错、被否决方向、背景信息、风险、待确认清单；追求覆盖全 |
| `项目记录/决策登记.md` | **已拍板/已冻结事项台账** | 每条结论一行：日期 / 事项 / 结论 / 依据 / 状态（已冻结·生效中·待定）；**动手前先扫，有分歧先查（§3）** |
| `项目记录/实际进度.md` | 完成台账（事实层） | **只记已发生的事实**：谁、哪天、交了什么、状态、卡点；**不复制计划**（计划归开发记录），避免两处对不上 |
| `计划和任务/任务清单.md` | 对外分发版（**唯一分发件**；PDF 已停用，2026-10-12） | 「谁、什么时候、交什么」的简版；已完成标 ✅、不删任务；与《开发记录》同步，**冲突时以《开发记录》为准**；改动后重跑 `生成任务清单.py` |

## 更新时机

项目出现任何进展（选型定案、代码跑通、测试结果、分工调整、踩坑）后，回读最新对话/群记录，同步更新两份文件。

## 更新流程

1. 判断归属：确定方案 → 开发记录；过程/教训/背景 → 经验与踩坑；已完成的事实 → 实际进度
2. 修改正文；同步更新文件头"最后更新"日期与版本号
3. 在两份文件的"变更记录"各加一行（无实质变化的文件注明"版本同步"）
4. 涉及分工、节点、交接的改动 → 重生成 `计划和任务/` 的清单与 PDF（`python 生成任务清单.py --build`），并同步 `实际进度.md`

## 写作要求

- 开发记录：只写当前有效规则，避免"之前/曾/改为"等返工痕迹词
- 经验与踩坑：写清"现象 → 原因 → 应对"；未闭环的尝试保留在试错记录
- 版本号：**各文件独立编号**（实质更新 +0.1，如 v1.23 → v1.24）；同一轮的更新，各文件的“最后更新”**日期保持一致**，便于对照
- 两份文件头部的"最后更新：日期 · 版本"必须一起改（只改正文不改头部 = 漏改）

## 留言板规范（AI / 组员之间的交接板）

> 位置：仓库根 `留言板.md`（跨工作区）＋ 各工作区自己的（现在只有 `firmware/留言板.md`）。
> 定位：**代码注释、聊天记录都放不下的那种话**——意图（我为什么这么改）、交接（这摊活交给谁）、提醒（别踩我这个坑）。

### 放什么 / 不放什么

| 内容 | 去处 |
|---|---|
| 交接 / 意图 / 提醒（短）| **留言板** |
| 进度（谁哪天做了什么）| `项目记录/实际进度.md` |
| 方案、长分析、建议 | 写成正式文档（如 `项目记录/A02避障算法迭代建议.md`）；留言板**只留一行指针** |
| 数据 / 证据 | `logs/`（入库只放 `共享_*.md`）|
| “必须怎么做”的规矩 | `docs/` |

### 硬规矩

1. **一条 ≤3 行、≤150 字**：**事 / 依据 / 要对方**（没有诉求就写“仅告知”）；
2. **必须署名**（谁 · 谁的 agent）；
3. **单独提交**：留言不和其他改动混在同一个提交里；
4. **只改自己的留言**，别改别人的；
5. **提交后必须在当轮回复末尾把留言原文贴给用户（组长）过目**；用户有异议 ⇒ 由作者**撤回该条并提交清空**；
6. **及时但别刷屏**：有事就写（尤其交接与“我刚改了什么”），没事不为写而写；宁可写得**详细而有价值**；
7. **上限 20 条**：超出时把最旧的移进同目录 `留言板归档_YYYY-MM.md`；
8. 要开新的工作区留言板，先满足一条：**该区 ≥2 个 AI 会改同一批文件**；否则用仓库根那块。

### 模板

```markdown
### [2026-10-10 21:40] 署名（谁 · 谁的 agent）→ 对方
- **事**：一句话说清做了什么 / 要对方注意什么
- **依据**：为什么这么改（带证据：文件名 / 行号 / 提交号 / 日志）
- **要对方**：需要对方做什么（没有就写“仅告知”）
```

## 目录纪律

- 根目录只保留：`README.md`、`说明书.md`、`AGENTS.md`、**`留言板.md`**、`拉取.bat`、`提交.bat`、**`工具箱.bat`**、`蓝牙日志.bat`、`logs/`（仅 `共享_*.md` 与 README 可入库）、`.gitignore`、`.gitattributes`、`项目记录/`、`计划和任务/`、`docs/`、工作目录（`firmware/`、`hardware/`、`mech/`、`tools/`、`报销/`）、`参考资料/`
- 各工作区的入口约定：`<区>/README.md`（给人）＋ `<区>/agent对接.md`（给 AI）＋ 区内 `留言板.md`（需要时）
- 临时产物放 `参考资料/临时解析文件/` 或删除
- `参考资料/原文件/` 为只读原件
