> 最后更新：**2026-10-01**（新增 §0「不确定的事不许写成确定的事」铁律）

## 0. 铁律：**不确定的事，不许写成确定的事**（2026-10-01 用户要求）

> 这份仓库是**给多个 AI + 多个人共读**的。一句写得太满的结论，会被下游 AI 当成事实继续传播，
> 最后没人知道它其实只是**推测** ⇒ 越改越错还没人发现。

| 场合 | 写法 |
|---|---|
| **代码事实 / 协议约定 / 实测读数**（可复现、有出处）| 可以写肯定 = 是 / 等于 / 显示 |
| **故障真因的推断** | ❌"真因是 X" ⇒ ✅"**证据指向 X**（附证据：日志/寄存器读数/复现步骤）；**不排除** Y、Z" |
| **物理/机械的解释**（打滑、丢脉冲、零偏、装配误差…）| ❌"说明是打滑" ⇒ ✅"**疑为**打滑；也可能是轮距取值不对 / 编码器丢脉冲 / 陀螺零偏，**尚未分辨**" |
| **标定值 / 尺度 / 估算**（如 mm/计数）| 必须标：**名义值（推定）** + 依赖的假设 + 已知误差量级 + "未精标" |
| **单次实测的结论** | 标样本量："**单次**实测（1 趟）"，不要写成"稳定/总是/已经没问题" |
| **目测 / 记忆 / 转述**（如"跑道大约 10m"）| 标"**目测**/**转述**，未核实" |

**用法**：写结论时先问一句"**这个我能复现吗？**"——不能复现的，一律降级为"推定/疑似/待验证"。
看到别人（或别的 AI）写了过满的结论，**顺手降级**，并在 `项目记录/经验与踩坑.md` 留一条为什么。

## 项目记录三个文件 + 对外清单 的分工

| 文件 | 定位 | 内容标准 |
|---|---|---|
| `项目记录/开发记录.md` | 正向流程（纯净） | 只写"现在应该怎么做"：方案、分工、接口、物料、进度、里程碑；不写试错与返工过程 |
| `项目记录/经验与踩坑.md` | 全量记录（不降噪） | 踩坑、试错、被否决方向、背景信息、风险、待确认清单；追求覆盖全 |
| `项目记录/决策登记.md` | **已拍板/已冻结事项台账** | 每条结论一行：日期 / 事项 / 结论 / 依据 / 状态（已冻结·生效中·待定）；**动手前先扫，有分歧先查（§3）** |
| `项目记录/实际进度.md` | 完成台账（事实层） | **只记已发生的事实**：谁、哪天、交了什么、状态、卡点；**不复制计划**（计划归开发记录），避免两处对不上 |
| `计划和任务/任务清单.md`（同名 PDF） | 对外分发版 | 「谁、什么时候、交什么」的简版；与《开发记录》同步，**冲突时以《开发记录》为准**；改动后重跑 `生成任务清单.py --build` |

## 更新时机

项目出现任何进展（选型定案、代码跑通、测试结果、分工调整、踩坑）后，回读最新对话/群记录，同步更新两份文件。

## 更新流程

1. 判断归属：确定方案 → 开发记录；过程/教训/背景 → 经验与踩坑；已完成的事实 → 实际进度
2. 修改正文；同步更新文件头"最后更新"日期与版本号
3. 在两份文件的"变更记录"各加一行（无实质变化的文件注明"版本同步"）
4. 涉及分工、节点、交接的改动 → 重生成 `计划和任务/` 的清单与 PDF（`python 生成任务清单.py --build`），并同步 `实际进度.md`

## 写作要求

- 开发记录：只写当前有效规则，避免"之前/曾/改为"等返工痕迹词
- 经验与踩坑：写清"现象 → 原因 → 应对"；未闭环的尝试保留在试错记录
- 版本号：**各文件独立编号**（实质更新 +0.1，如 v1.23 → v1.24）；同一轮的更新，各文件的“最后更新”**日期保持一致**，便于对照
- 两份文件头部的"最后更新：日期 · 版本"必须一起改（只改正文不改头部 = 漏改）

## 目录纪律

- 根目录只保留：`README.md`、`说明书.md`、`AGENTS.md`、`拉取.bat`、`提交.bat`、`面板.bat`、`蓝牙日志.bat`、`logs/`（仅 `共享_*.md` 与 README 可入库）、`.gitignore`、`.gitattributes`、`项目记录/`、`计划和任务/`、`docs/`、工作目录（`firmware/`、`hardware/`、`mech/`、`tools/`、`报销/`）、`参考资料/`
- 临时产物放 `参考资料/临时解析文件/` 或删除
- `参考资料/原文件/` 为只读原件
