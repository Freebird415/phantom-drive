## 3. 已澄清的重要事实（防止重复走弯路）

1. **"视觉模块"不存在**：王政淋名下所谓视觉模块，实为另一套八路红外/灰度传感器 → 本项目无摄像头方案，避障只能靠超声波 / ToF / 红外等
2. **旧车是"双轮自平衡 + 循迹"小车**：只能参考结构与拆件用料，不能直接改造成比赛车；且规则要求车架自制（一票否决）
3. **车架自制的边界**：允许螺丝、轴承等标准件，但**主结构**必须队伍自行设计 + 用中心设备加工，答辩要提供 CAD 源文件与加工照片/视频；"完全买现成"直接 0 分且不予参赛
4. **停止分是"精停"**：过终点线后车**尾**投影不得越过终点线
5. **时间分是相对值**：40 × t₁/t₂（对自己以外全场最快队）→ 时间快慢直接影响分数，不是"不被取消资格"那么简单
6. **非避障脱线要扣分**：脱线期间经过的赛段不计分 → 绕障必须"短、快、可控"
7. **电机很强**：JGB37-520 12V 333RPM + 大轮 ≈ 1 m/s 以上空载 → 算法必须限速起步，否则第一圈就跑飞
8. **车小有利避障**（规则原话）且尺寸上限 250×200×200mm 是每轮 −10% 的红线
9. **个人账号私有仓库的协作者只有"读写"一档**（GitHub 官方文档原文）：界面没有角色下拉框，也无法设只读/管理员；要细分权限只能把仓库转到组织（Organization）下——本项目不需要折腾
10. **电机是带编码器版本**（第 3 周确认）：JGB37-520 为 6 线（电机± + 编码器 VCC/GND/A/B）；BOM 已备编码器 6p 接口，引脚表已预留两路定时器编码器模式（TIM2/TIM4）。**不同批次线色可能不同，接线前必须实测复核**
11. **Blue Pill 板载 8MHz 晶振占用 PD0/PD1**：虽然固件用 HSI 8MHz→PLL→64MHz 不依赖它，但板上晶振仍物理连接 → **PD0/PD1 不可当 GPIO**；引脚预算按 35 个可用 IO 算（PA0~15 + PB0~15 + PC13~15）
12. **本项目的核心板还焊了一颗 32.768kHz 晶振**（实物照片：晶振旁黑方块丝印 `32768`）→ **PC14/PC15 也不可用**，可用 IO 降到 **33 个**（PA0~15 + PB0~15 + PC13）
13. **核心板的 4pin SWD 排针不含 NRST**（只有 3V3/SWDIO/SWCLK/GND）→ 必须自己再做一个含 NRST 的 5pin 排针，否则关了 JTAG 后跑飞就没法“连接下复位”就回
14. **实物亚博灰度是 YB-MUX04-2.0**，针序 `5V GND KEY RESET X1..X8 TX RX SCL SDA`；它**没有**老教程里的 AD0/AD1/AD2 + OUT 多路复用线（那是旧型号）→ 引用亚博资料时要注意新旧不一致，以**实物丝印为准**

## 4. 踩坑清单 / 避坑指南

### 电气
- 杜邦线靠摩擦接触，振动（车轮/电机/急转）下会间歇性松动——**间歇性故障是最难查的一类 bug**；成品禁用，连接规范见《开发记录》
- 电机动力线不能用细杜邦（24–26AWG 单针 ≤1A），JGB37-520 堵转可达 2A+
- **单电源**是规则硬要求（两块电池 −10%/轮）→ 12V 主电池 + 降压是唯一正解
- 电池必须加总开关与保险丝（规则也明确建议，防调试短路）
- 光电门相关：**车上的红外补光灯若水平朝前，可能提前触发对射光电门**（影响计时）→ 补光朝下并加遮光罩
- 国内打板/快递可能被国庆拖慢 → **PCB 9/30 前下单**（节前最后窗口）、**10/11 前点亮**

### 传感器与环境
- 红外/灰度怕环境光：广告布反光、现场灯光变化 → 加遮光罩 + 现场标定；这也是"传感器选型要抗光"的由来
- **光电门三种干扰**：①超声波可能把门柱当障碍物（起终点附近应设"禁避障区"）②车灯可能误触发计时 ③门附近光照/读数可能跳变（需现场实测 10 分钟验证）
- **回环赛道**：起始段有大回环，双线可能同时进入八路传感器视野 → 需要专门策略（如靠单侧）
- **障碍物每轮随机摆放**（线的任意一侧）→ 绕障逻辑必须能自动判侧
- **两个 HC-SR04 必须分时触发**：同时发波会收到对方的回波（串扰）→ 各自独立 Trig 引脚 + 软件串行触发，两次测距至少间隔 60ms（等上一发余波衰减）
- **HC-SR04 的 Echo 是 5V 输出**：STM32F103 的 PA/PB 多数是 FT（5V 容忍）脚，仍建议串 1k + 2k/3.3k 分压（或 3.3V 钳位二极管），防上电瞬态与走线串扰
- **超声波看不到细柱**：HC-SR04 波束角约 15°，对细杆（光电门立柱、障碍物边缘）回波弱 → 起终点附近必须设禁避障区，避障判定加连续帧确认

### MCU 与引脚（第 3 周新增）
- **关掉 JTAG 可多出 3 个 IO**（PB3/PB4/PA15）：只用 SWD 调试时关掉 JTAG 即可；代价是**必须把 NRST 引到调试排针**，否则一旦程序跑飞或关闭 JTAG 的时机不当，就只能靠 BOOT0 跳线救板
- **PA11/PA12 是板载 USB 的 DM/DP**：部分克隆板在 PA12 上有 1.5k 上拉电阻 → 用作普通 IO 前要核对板型/丝印（本项目不用板载 USB，PA12 只作输出、PA11 拿去做 STBY）
- **PC13/PC14/PC15 驱动能力弱且不耐 5V**（只能小电流输出、不可作 5V 输入）→ 只放 LED 或作输入用
- **TB6612 的 AIN/BIN/STBY 要加 10k 下拉**：MCU 复位期间引脚是高阻，无下拉时电机可能被干扰误动 → 硬件下拉 + STBY 保留跳线可强制使能
- **PB2 是 BOOT1，不能当普通 IO**（v3.0 新增）：复位期间 PB2 被拉高 → MCU 从 **SRAM** 启动而不是 Flash → 现象是"上电固件不跑"（用调试器又能跑）→ 本项目把 PB2 标为**保留勿接**（不能接按键、不能接复位时可能输出高电平的传感器）
- **TIM2 Full Remap 会与 USART2 抢 PA2/PA3**（v3.0 新增）：Full Remap 把 TIM2_CH3/CH4 复用到 PA2/PA3，而 PA2/PA3 同时是 USART2 默认脚 → 本项目**不用 TIM2**（保持默认映射），编码器改用 TIM4+TIM3
- **PA11 只能作输出**（原 USB DM）：拿来做 PWM 输出正好，**不能拿来做输入**
- **看引脚不能只看"能不能用"，还要看"复位期间它是什么电平"**：BOOT0/BOOT1、JTAG 脚、USB 脚都属于这类雷区

### OLED 中英文显示 · 2026-09-23 实测

**① 中文字库必须"子集化"，不能整库进 Flash**
一个完整中文字库几 MB，而 STM32F103C8T6 只有 **64KB Flash**（当时固件已用 ~30KB）。
做法：`tools/生成字库.py` 用 **PIL + simhei.ttf** 把**用到的字**渲染成 16×16 点阵，输出 `font_subset.h`。
实测：**ASCII 95 字（570B）+ 汉字 38 字（1216B）≈ 1.9KB**，完全放得下。

**② 新增汉字忘加进字表的坑（做了自动报警）**
现象：屏幕上那个字画成**空心方框**，或者干脆空白，很难定位。
应对：`Ol_Text()` 查不到字模时**画空心方框 + 串口打印** `# 字库缺字：UTF-8 xx xx xx → 请加进 CN_CHARS`。
流程：**改 `tools/生成字库.py` 的 CN_CHARS → 重跑脚本 → 重新编译**，三步缺一不可。

**③ 字模生成的阈值很关键**
PIL 渲染后要二值化：阈值太高（如 200）→ 笔画细的字**缺笔画**；太低（如 50）→ **糊成一团**。
实测 **阈值 110** 对 16×16 黑体效果好；ASCII 用 consola.ttf 渲染到 6×8 会略毛糙（可读，但不如真位图字模锐利）。

**④ 汉字占 2 页，画的时候要同时改 page 和 page+1**
SSD1306 是页寻址（每页 8 行）：16×16 汉字跨 **2 页**，`fb[page]` 放上半 8 行、`fb[page+1]` 放下半 8 行。
只写一页 → 汉字只显示上半截（这个现象很有迷惑性，容易误判成"字模坏了"）。

**⑤ 先建帧缓冲再一次性刷屏**
不要在循环里逐字发 I2C（100 个字符 = 100 次传输，又慢又容易半屏）。用 `s_fb[8][128]` 画完再 `Ol_FbFlush()`。

**⑥ 实测结论**：`OLEDTXT` 测试页四行（ASCII 符号行 / 中文显示测试 / 状态速度偏差左右 / 英文长串）**一次成功，零缺字**。

### OLED（0.96" SSD1306）· 2026-09-23 实测

**① 型号/地址/上拉全靠"拍背面丝印"确认**
背面丝印 `0.96 OLED` + `IIC ADRESS SELECT 0x78` + `R5/R6/R7/R10 = 472`：
→ **SSD1306**（0.96"+I2C 基本都是它；SH1106 多为 1.3"）、**7bit 地址 0x3C**、**板载已有 4.7k 上拉**。
不用猜、也不用另加电阻。

**② 板载上拉是拉到 VCC 的 → 所以 VCC 必须是 3.3V**
这条是本元件最容易犯的错：若图方便接 5V，OLED 自己的 4.7k 就把**整条 I2C2 拉到 5V**；
现在只有 OLED 时看不出问题，但将来挂上 **MPU6050（3.3V 器件，SDA/SCL 极限约 VDD+0.3=3.6V）就会被 5V 打坏**。
→ **OLED VCC 一律接 3V3**（顺带 I2C2 也是 3.3V 总线，与规划一致）。

**③ 两条 I2C 总线绝不能混**
I2C1（PB8/PB9，上拉 **5V**）只挂灰度；I2C2（PB10/PB11，上拉 **3.3V**）挂 OLED/MPU6050。
把 OLED 插到灰度那条 16P 座上 = **5V 打坏 SSD1306**。

**④ 0.96" 有"上黄下蓝"双色面板，不是花屏**
面板上 16 行黄色、下 48 行蓝色是**屏体类型**，不是驱动问题。测试图案在上半屏显示为黄色属正常。

**⑤ bring-up 用棋盘格比点亮全屏更有信息量**
棋盘格 + 四周边框能同时检验**行/页寻址、列扫描、每点独立控制**；
"全屏点亮"只能证明供电和电荷泵正常，暴露不出寻址错误。

**⑥ 排查口诀**：先 `OLSCAN`（只探地址）再 `OLED`（初始化+图案）。
地址不应答 = 总线层问题；应答了但屏不对 = 初始化参数/驱动型号问题。

### 超声波（HC-SR04）· 2026-09-23 实测（面包板 bring-up）

**① 命令处理写在串口中断里 → 输出会被静默丢掉**
现象：`US` 调试命令的回复时有时无；有时只跑一半。
原因：中断里的 `printf` 和主循环的 `printf` 抢同一个 UART，`HAL_UART_Transmit` 返回 BUSY，输出直接丢弃；而且命令里的 `HAL_Delay` 还把中断给堵住了。
应对：**中断里只收行，命令执行放到主循环**（`Tlm_Poll()`）。这也顺手把“阻塞几十毫秒的中断”这个隐患一并去掉了。

**② 两个触发源各测各的 → 撞出假的“超量程”**
现象：`$U` 里出现大量 `width=30002µs`（正好卡在 30ms 超时）→ 判为 −2 “没回波”；但同一颗探头单独测却是 100%。
原因：主循环每 100ms 测一颗、`US` 命令又自己测一轮 → **同一颗模块被过密触发**；HC-SR04 被短间隔重触发时 Echo 会拖成一条长高电平。
应对：**把节拍守则放到驱动层**（`Us_Read()` 内部判断距上次触发是否够 60ms，不够就返回 `-6` 并不真触发）——不管谁来调都不会撞。

**③ 测量失败后继续密集重触发 → 模块把自己锁死**
现象：某颗一旦开始报 −2，就会连续报下去；而且这个“卡死”状态会在两颗之间游走（上一轮左好右坏，下一轮反过来）。
原因：HC-SR04 在“没回波”时会输约 200ms 长高电平；在这段时间里继续触发，它就缓不过来。
应对：**失败后把该颗的恢复间隔拉到 600ms**（`US_RECOVER_MS`，成功时只需 60ms）——实测能把卡死状态自动解开，恢复 100%。

**④ 探头离反射面 < 20cm 时不可靠（关键物理规律，与代码无关）**
实测规律：**≥ 20cm 的所有读数都是 100%；< 20cm 就掉到 37~58%**。
原因：发射后振子还在余振，16cm 的回波只用 ~0.96ms 就回来了，落在余振里分不出来 → 报 −2。数据手册写“2cm 起”，但**廉价模块实际可靠下限普遍在 20~30cm**。
应对：**安装高度/前置距离按 ≥ 25~30cm 设计**（赛车避障本来就在 30cm 以上才有意义）。

**⑤ 波束角只有 ~15°，歪 10° 就整个打偏**
现象：手握两颗时，一颗读 206mm、另一颗读 575mm；转正后两者立刻变成 322/332mm（一致）。
应对：探头必须**平行正对**同一反射面；调试时不要手持（手抖 + 歪角），把探头垫高放稳、用手拿反射物。

**⑥ 杜邦线掉一根就变 “完全无反应”**
现象：左探头从“偶尔测不到”变成 100% 报 −1（触发后 Echo 从头到尾没动过）。
原因：**GND 杜邦线从面包板里脱出来**（就是本项目早就记过的“杜邦线靠摩擦接触”那个坑）。
应对：`-1` 优先查线（Trig / Echo / VCC / GND 四根都按一下），不要先怀疑代码或模块。

### MPU6050 · 2026-09-23 实测

**① 和 OLED 共用 I2C2 是零成本的**
I2C 是总线协议，地址不同即可共存（OLED `0x3C` + MPU `0x68`）；两条线现成、上拉现成（OLED 板载 4.7k）。
→ 这也是「别急着删它」的核心理由：**它不占任何额外引脚，只占一个 4P 座**。

**② VCC 必须 3.3V（和 OLED 同一条总线，别混电压）**
MPU6050 的 SDA/SCL 极限约 VDD+0.3=3.6V；而 **I2C1（灰度）是 5V 上拉总线** → 把 MPU 挂上去会被打坏（同理 OLED）。

**③ 验证加速度计对不对，最快的判据是「模长≈1g」**
静止时 `√(ax²+ay²+az²)` 应 ≈ **1.0 g**（实测 1.04 g ✓）。
这比「看数值有没有变化」强得多 —— 它同时验证了量程配置、符号、换算系数、读取顺序都对。

**④ 陀螺仪静止也有零偏，用之前必须标定**
实测静止时 x 轴有 −2~−5 dps 的漂动。这不是坏，是 MPU6050 的常态：
真要用角速度，第一步是**静置采几百个样本取均值当零偏**，之后读数都要减掉它。

**⑤ 定位（决策 E-24）：它是诊断仪器，不是控制输入**
循迹车的基本信息是「线在哪」（八路灰度给），陀螺仪的航向是冗余的；
它真正的价值是**看振动／加减速冲击／碰撞尖峰**，以及 PID 调参时区分「传感器噪声 vs 转向过冲」。
→ 硬件保留座子、软件优先级最低；遇到「找不到原因的抖动／振荡」时再插上诊断。

### 按键 / 蜂鸣器 · 2026-09-23 实测

**① 四脚轻触开关是"两两连通"的 —— 插错脚会永远不动作（本次实际踩到）**
现象：按住按键，固件读到的还是"松开"；换面包板孔位后立刻正常。
原因：4 脚轻触开关**同一侧的两个脚内部本来就短接**，把线插在同一侧 = 开关永远不参与通断。
应对：**用对角线的两个脚**（或跨到另一侧）。**秒判**：万用表通断档量两个脚 —— 不按不通、按下通才对。
（本次最终原因就是面包板插错孔，不是代码/引脚问题）

**② 按键状态要"两个状态都确认"才算验完**
只测到"按下"不够：还要确认**松开时能回到另一个电平**。
本机实测：松开 `PA12=1`（核心板 1.5k 上拉 + 内部上拉）、按下 `PA12=0` → 两个状态都对才收工。

**③ 蜂鸣器绝不能直接挂 GPIO**
有源蜂鸣器 20~30mA，超 STM32 单脚能力；且感性负载断电有反电动势。
正确：`PB15 → 1k → NPN(S8050) 基极`，发射极→GND，集电极→蜂鸣器负极，蜂鸣器正极→3V3，**两端并续流二极管**。
高电平 = 三极管导通 = 响。

**④ 排查顺序（本次证明有效的三步）**：先 `KEY` 读电平（不动）→ 再用万用表量 PA12 对 GND（松开 3.3V / 按下 0V）→ 最后查物理接插件。
**"读数不变"先怀疑接插件**（面包板孔位/杜邦线/开关脚位），这条在本项目已经连续命中三次（灰度 GND、编码器插错排针、按键错孔）。

### 编码器（JGB37-520 自带，硬件编码器模式）· 2026-09-23 实测

**① `TIM_Encoder_InitTypeDef` 用 `{0}` 初始化 → 计数自己狂跑（最坑的一条）**
现象：两路计数每 0.5 秒自己涨几千，看起来像"输入悬空拾噪"或"编码器在转"。
原因：`{0}` 让 `EncoderMode = 0`，而合法值只有 `TI1`(1) / `TI2`(2) / `TI12`(3)；
**模式为 0 = 从模式关闭 → 定时器退回用内部 64MHz 时钟计数**，16 位计数器每秒回绕上千次。
应对：**必须显式写 `enc.EncoderMode = TIM_ENCODERMODE_TI12;`**（两通道都计，4 倍频）。
教训：HAL 的结构体初始化里，**"0 有语义"的字段不能靠 memset 蒙**。

**② 判断"是噪声还是真在动"→ 先看静止基线**
连读 3 次静止值：`Δ = 0` 才说明输入干净；若静止就漂 → 查 VCC/A-B 是否悬空。
本次两路静止都是 0 → 之前看到的"漂移"其实是人手在转轮子，不是噪声。

**③ C1/C2 反接只影响符号，不用重新接线**
A/B 是正交两相，交换只是把相位反过来：**计数照样准、不丢数、每圈计数一样**，只有**正负方向相反**。
应对：用软件集中修正（`ENC_SIGN_L/R`、`MOT_SIGN_L/R` 宏），**不动机器、不动线**（减少接触不良的机会）。
符号的正式对齐放在**电机能通电转的那次**做（那时才知道"哪个方向算前进"）。

**④ "物理轮子 ↔ 逻辑通道"怎么定？→ 转一个轮子看哪路在动**
本次踩到：新电机编码器**还插在 PB6/PB7**（老通道）→ 表现为"转新轮子，动的却是 L"。
排查范式：清零 → 静止确认基线 → 只转一个轮子 → 看哪路在动 → 就能把映射关系钉死。

**⑤ 验收结论**：两路都通过（左 TIM4/PB6·PB7、右 TIM3/PA6·PA7），
手转增量均匀（每次 ~200 counts / 0.45s ≈ 460 counts/s ≈ 20 RPM 手速），
转一路时另一路稳定为 0 → **两路独立、零丢数**。

### 灰度（感为八路 I²C）· 2026-09-23 实测

**① `KEY` 不是板上实体按键，是一个输入引脚**
现象：想在板上找按键却只看到“母头”。
应对：**用杜邦线短接 16P 的针 3（KEY）↔ 针 1（GND）** 代替按下；
短接~0.2s = 短按，保持~4s = 长按。
校准关键：**长按只是“进校准模式”，本身不记录**；之后要分别在黑场、白场各**短按**一次，**灯灭 = 校准完成**。

**② I²C 上拉必须是 5V —— 面包板上最容易搞错的一条**
现象：ping 永远 FAIL，但模块 LEDs 亮着（供电正常）。
原因：面包板上没有上拉；或误以为“3.3V 器件就用 3.3V 上拉”。
应对：**插上模块板载的「SCL上拉 / SDA上拉」跳帽**（板载 5V/10k）——手册要求外置上拉源 **≥72% 供电电压 = 3.6V**，
3.3V 不达标；且**一条总线只能有一处上拉源**。PB8/PB9 是 FT 脚，允许 5V 上拉。

**③ 地址跳线会改地址**
插 AD0/AD1 会把 7bit 地址从 **0x4C** 变成 0x4D~0x4F（驱动就是按 0x4C 写的）。
调不通时先跑总线扇描（`GRSCAN`）：**一个都不应答 = 总线层没通；应答 0x4C = 一切就绪**。

**④ `ana` 全 0 + `dir` 全 0 = “没照到东西”，不是校准坏了**
模拟量是**物理测量**（不受校准影响）：全 0 只说明探头悬空/离面太远。
手册检测高度 **4~100mm，典型 20mm**。判据：贴着白面包板扫时 `ana` 应有 **50~100 counts** 的摆幅（实测 18~134）。

**⑤ 数字判定必须和模拟量交叉验证才算调通**
只看 `dir` 分档不够（可能是校准门限凑出来的）。**强证据**：判“黑”的那几路，`ana` 也正好是最高的那几路；
扫面包板时各通道按 **6→5→3→7→1** 依次起伏 → 证明**物理顺序、灵敏度、独立性全对**。

**⑥ 校准后不得改变安装高度；但装车/赛前必须重校**
手册原文：每次更改安装高度都应重新校准，且传感器对距离敏感。断电不丢记忆（不用每次上电重校）。
→ 面包板上校的准只是“面包板工况”的；**装到车上（高度/角度变了）、以及比赛现场（光照、胶带材质变了）都要重新校准**。

### I²C 与供电（第 3 周新增，最容易烧器件）
- **灰度模块的板载上拉是 5V（10k）**（感为手册原文）→ 若把 3.3V 器件（SSD1306 OLED、MPU6050）挂到同一条总线上，**SDA/SCL 会被拉到 5V，超过它们约 3.6V 的极限，会烧** → 本项目把两条总线拆开：I2C1（灰度，5V 上拉）与 I2C2（OLED+MPU6050，3.3V 上拉）**绝不并联**
- **STM32F103 的 PB8/PB9 是 FT（5V 容忍）脚**，open-drain 模式下允许总线上拉到 5V → 跟 5V 传感器通信没问题；但**不可把 5V 上拉总线接到任何非 FT 脚**
- **一个 I²C 总线上只允许一处上拉源**：板载有上拉时 PCB 不要再并 3.3V 上拉，否则等效上拉变成高压侧，仍会打坏低压器件
- **专用电机排线里混着编码器信号**：JGB37-520 的 6 芯线同时走 M+/M−（2A 级、PWM 开关）与编码器 A/B/VCC/GND → 噪声耦合会丢计数；应对：A/B 串 100Ω + 并 1nF，编码器 VCC 就近 100nF，固件再做“最大跳变”过滤
- **电机侧连接器选型要注意额定电流**：JST-XH 触点约 3A，而 JGB37-520 堆转可到 2A+ → 堆转不要久留，否则座子发热
- **核心板自带 LDO（RT9193）与自备 LDO 不能同时对打**：5V 脚与 3V3 脚只能接一个；本项目只送 5V，3.3V 由核心板输出（≤300mA，需核算负载）

### 工具与脚本
- **Windows 批处理（.bat）不能存成 UTF-8**：含中文的 UTF-8 .bat 会让 cmd 解析器错位（报「命令语法不正确」或把半行中文当命令执行）→ 必须存成 GBK 编码 + CRLF 换行
- **控制台代码页与 git 输出冲突**：git 输出是 UTF-8，中文 Windows 控制台默认 GBK（936），直接显示会让中文文件名/提交信息乱码 → 在 git 命令前后临时 `chcp 65001` / `chcp 936` 切换（脚本已内置）
- **用 `for /f` 抓取 git 配置时要先切 65001**：cmd 变量内部是 Unicode，抓取时按当时代码页解码；936 下抓 UTF-8 输出会导致中文被「双重转换」变成乱码（显示正常但内容是错的）
- **`git reset --hard` 会删掉“已 git add 但未提交”的新文件**（未 add 的 `??` 文件则会保留）→ 想做“只还原不删新文件”的工具，必须先在 reset 前执行 `git reset -q` 取消暂存
- **批处理文件的换行符必须统一成 CRLF**：混用（例如补丁只给新增部分写了 LF）会让 cmd 解析错位，报出一堆“xx 不是内部或外部命令”的碎片错误 → 每次改完 .bat 都要检查
- **测试 .bat 时注意两类假象**：①测试脚本若未提交，会被 `git clean -fd` 删掉导致 cmd 读串；②测试脚本若是“已修改的跟踪文件”，会被 `reset --hard` 中途还原导致同样问题 → 正确做法：把“输入已固定”的测试脚本提交并推送到沙盒远端，保证与远端一致
- **PlatformIO + stm32cube 框架（无 CubeMX 生成的 `it.c`）必须自己写 `SysTick_Handler`**：`HAL_Init()` 会开 SysTick 中断做毫秒计时，缺处理函数就跳进“默认处理器”的死循环——现象是 **LED 不闪、串口无输出、像死机**，但用调试器看会发现时钟/UART 寄存器都已正确初始化。排查捷径：`openocd` 里 `reg xpsr`，IPSR（低 9 位）= 15 即卡在 SysTick
- **读串口的脚本不要写 `while True: readline()`**：小车 100Hz 持续输出时永远读不完 → 用“限时循环”或设行数上限
- **PlatformIO 首次编译要联网**：会自动下载工具链与框架（约 200MB，国内需代理，5~15 分钟）；之后的增量编译只要几秒
- **`printf` 打印浮点要加链接参数** `-Wl,-u,_printf_float`（否则 `%f` 输出空或错乱）
- **HAL 的 `HAL_xxx_MspInit` 不能加 `static`**（HAL 头文件里是非静态声明，加了会编译报错）
- **自动化测试 `set /p` 的三个坑**：①**批量送入**（管道 / 重定向 / SendKeys 瞬时连发）会被 `set /p` 当“整行”读走，只有真实逐字键盘输入才按行读；②喂给重定向的输入文件**必须是 CRLF**，LF-only 会让第一行把后续内容全吃掉；③**`chcp 65001` 执行过后，重定向 stdin 下的 `set /p` 一律读到空**（真实控制台键盘输入不受影响）→ 测试交互脚本时先用无 `chcp` 的逻辑副本验证分支，再用真实控制台冒烟
- **`.bat` 里中文 `echo` 不能放在 `chcp 65001` 与 `chcp 936` 之间**：脚本本身是 GBK，控制台处于 UTF-8 时会显示成乱码 → 只让 git 输出留在 65001 段内，中文提示一律放在段外
- **“拉取并提交”合在一个脚本里是设计缺陷**（2026-09-13 修正）：它诱导“先改再拉”，一旦别人也改了同一处就会撞车 → 拆成「拉取.bat」（开工前）+「提交.bat」（收工时），顺序直接由脚本名固定下来；并把“已拉取？”做成 `提交.bat` 里的确认页（拉取 → 放入 → 提交），把提醒做进流程而不是只写在文档里
- **ChatGPT 的 GitHub 连接器是“用户级授权”，协作者也能读**（2026-09-13 实测）：一度以为“只有仓库所有者能用”——那是 GitHub App **安装**的规则（只能装到自己名下的账号）；这个连接器不走安装，GitHub 侧显示在 `Settings → Applications → Authorized GitHub Apps` 里的 `ChatGPT Codex Connector`（Owned by openai），而 `Installed GitHub Apps` 里是空的 → 访问范围 = **你自己 GitHub 账号对仓库的权限**，所以仓库协作者在自己的 ChatGPT 里连接自己的账号即可读。坑点：一直在找“选仓库 / Configure”是白找
- **测试建议**：脚本改动后用「固定值替换输入」的方式在沙盒仓库（裸仓库 + 克隆）里跑完整流程，比真实键盘更可控
- **LaTeX `standalone` 类在 xelatex 下不会自动裁边**：页面仍是 letter 尺寸，**长图会被截掉尾部**（本项目第一版接线图就丢了最后一栏）→ 用 `preview` 宏包（`\usepackage[active,tightpage]{preview}` + `\PreviewEnvironment{circuitikz}`）把页面设成内容尺寸；但 **`preview` 与 `standalone` 同时加载会产出 15 字节的空 PDF**，两个只能留一个
- **xelatex 输出中文要 xeCJK + 系统字体**（`\setCJKmainfont{Microsoft YaHei}`）；编译必须在 **ASCII 路径**的临时目录里做（中文路径下 pdftoppm / pdftotext 不稳，PowerShell 脚本也会被 cp936 误读）→ `hardware/电气设计/生成接线图.py` 就是这么做的
- **circuitikz 的 `node[pmos]` 默认是竖放的**，旋转后锚点跟着转，直接接 `(Q1.D)/(Q1.S)` 会接出一团乱线 → 评审图里改用「模块框 + 文字」表示未定器件
- **画原理图前先给版面定约定再落坐标**：本项目电源图把 12V/5V/3.3V/接地四条母线各占一条 y，并规定「12V 支路下拉全部落在 x ≤ 16.6、5V 支路落在 x ∈ [22,24]」，于是全图可证不相交——比事后靠肉眼找交叉省事得多

### 硬件与方案
- 连接方案演进：全杜邦（初版）→ 误以为全换 XT/T 插（纠正）→ **按电流分级**（电池 XT、信号 XH/PH 带扣、不拆装焊死、调试留杜邦）
- 车架方案候选：整体 3D 打印 / 铝方管 + 板材 + 3D 打印件（旧车路线，较成熟）/ 木板 + 热熔胶（快速原型）→ 待 M01 定案；必要时可先做快速原型供电控联调
- 避障传感器候选：超声波（便宜、不受光影响、但角度窄有盲区）/ ToF 激光（抗光好、精度高、稍贵）/ 红外避障（受光影响大，不推荐）→ **9/20 定案：HC-SR04 超声波 ×2（左右各 1）**，理由是便宜、不受环境光影响；代价是盲区大、与光电门可能互相干扰（见 §4 传感器与环境）
- 芯片方案：曾讨论是否换芯片 → 结论：STM32F103C8T6 现有 3 块、性能足够（64KB Flash/20KB RAM），沿用
- 调试方式认知：曾设想"人工描述现象让 agent 直接调" → 明确**前提是遥测链路**，否则是盲猜 → P01 反馈链路因此前置到抢跑期
