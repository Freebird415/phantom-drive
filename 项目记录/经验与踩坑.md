## 3. 已澄清的重要事实（防止重复走弯路）

1. **"视觉模块"不存在**：王政淋名下所谓视觉模块，实为另一套八路红外/灰度传感器 → 本项目无摄像头方案，避障只能靠超声波 / ToF / 红外等
2. **旧车是"双轮自平衡 + 循迹"小车**：只能参考结构与拆件用料，不能直接改造成比赛车；且规则要求车架自制（一票否决）
3. **车架自制的边界**：允许螺丝、轴承等标准件，但**主结构**必须队伍自行设计 + 用中心设备加工，答辩要提供 CAD 源文件与加工照片/视频；"完全买现成"直接 0 分且不予参赛
4. **停止分是"精停"**：过终点线后车**尾**投影不得越过终点线
5. **时间分是相对值**：40 × t₁/t₂（对自己以外全场最快队）→ 时间快慢直接影响分数，不是"不被取消资格"那么简单
6. **非避障脱线要扣分**：脱线期间经过的赛段不计分 → 绕障必须"短、快、可控"
7. **电机很强**：JGB37-520 12V 333RPM + 大轮 ≈ 1 m/s 以上空载 → 算法必须限速起步，否则第一圈就跑飞
8. **车小有利避障**（规则原话）且尺寸上限 250×200×200mm 是每轮 −10% 的红线
9. **个人账号私有仓库的协作者只有"读写"一档**（GitHub 官方文档原文）：界面没有角色下拉框，也无法设只读/管理员；要细分权限只能把仓库转到组织（Organization）下——本项目不需要折腾
10. **电机是带编码器版本**（第 3 周确认）：JGB37-520 为 6 线（电机± + 编码器 VCC/GND/A/B）；BOM 已备编码器 6p 接口，引脚表已预留两路定时器编码器模式（TIM2/TIM4）。**不同批次线色可能不同，接线前必须实测复核**
11. **Blue Pill 板载 8MHz 晶振占用 PD0/PD1**：虽然固件用 HSI 8MHz→PLL→64MHz 不依赖它，但板上晶振仍物理连接 → **PD0/PD1 不可当 GPIO**；引脚预算按 35 个可用 IO 算（PA0~15 + PB0~15 + PC13~15）
12. **本项目的核心板还焊了一颗 32.768kHz 晶振**（实物照片：晶振旁黑方块丝印 `32768`）→ **PC14/PC15 也不可用**，可用 IO 降到 **33 个**（PA0~15 + PB0~15 + PC13）
13. **核心板的 4pin SWD 排针不含 NRST**（只有 3V3/SWDIO/SWCLK/GND）→ 必须自己再做一个含 NRST 的 5pin 排针，否则关了 JTAG 后跑飞就没法“连接下复位”就回
14. **实物亚博灰度是 YB-MUX04-2.0**，针序 `5V GND KEY RESET X1..X8 TX RX SCL SDA`；它**没有**老教程里的 AD0/AD1/AD2 + OUT 多路复用线（那是旧型号）→ 引用亚博资料时要注意新旧不一致，以**实物丝印为准**

## 4. 踩坑清单 / 避坑指南

### 电气
- 杜邦线靠摩擦接触，振动（车轮/电机/急转）下会间歇性松动——**间歇性故障是最难查的一类 bug**；成品禁用，连接规范见《开发记录》
- 电机动力线不能用细杜邦（24–26AWG 单针 ≤1A），JGB37-520 堵转可达 2A+
- **单电源**是规则硬要求（两块电池 −10%/轮）→ 12V 主电池 + 降压是唯一正解
- 电池必须加总开关与保险丝（规则也明确建议，防调试短路）
- 光电门相关：**车上的红外补光灯若水平朝前，可能提前触发对射光电门**（影响计时）→ 补光朝下并加遮光罩
- 国内打板/快递可能被国庆拖慢 → **PCB 9/30 前下单**（节前最后窗口）、**10/11 前点亮**

### 传感器与环境
- 红外/灰度怕环境光：广告布反光、现场灯光变化 → 加遮光罩 + 现场标定；这也是"传感器选型要抗光"的由来
- **光电门三种干扰**：①超声波可能把门柱当障碍物（起终点附近应设"禁避障区"）②车灯可能误触发计时 ③门附近光照/读数可能跳变（需现场实测 10 分钟验证）
- **回环赛道**：起始段有大回环，双线可能同时进入八路传感器视野 → 需要专门策略（如靠单侧）
- **障碍物每轮随机摆放**（线的任意一侧）→ 绕障逻辑必须能自动判侧
- **两个 HC-SR04 必须分时触发**：同时发波会收到对方的回波（串扰）→ 各自独立 Trig 引脚 + 软件串行触发，两次测距至少间隔 60ms（等上一发余波衰减）
- **HC-SR04 的 Echo 是 5V 输出**：STM32F103 的 PA/PB 多数是 FT（5V 容忍）脚，仍建议串 1k + 2k/3.3k 分压（或 3.3V 钳位二极管），防上电瞬态与走线串扰
- **超声波看不到细柱**：HC-SR04 波束角约 15°，对细杆（光电门立柱、障碍物边缘）回波弱 → 起终点附近必须设禁避障区，避障判定加连续帧确认

### MCU 与引脚（第 3 周新增）
- **关掉 JTAG 可多出 3 个 IO**（PB3/PB4/PA15）：只用 SWD 调试时关掉 JTAG 即可；代价是**必须把 NRST 引到调试排针**，否则一旦程序跑飞或关闭 JTAG 的时机不当，就只能靠 BOOT0 跳线救板
- **PA11/PA12 是板载 USB 的 DM/DP**：部分克隆板在 PA12 上有 1.5k 上拉电阻 → 用作普通 IO 前要核对板型/丝印（本项目不用板载 USB，PA12 只作输出、PA11 拿去做 STBY）
- **PC13/PC14/PC15 驱动能力弱且不耐 5V**（只能小电流输出、不可作 5V 输入）→ 只放 LED 或作输入用
- **TB6612 的 AIN/BIN/STBY 要加 10k 下拉**：MCU 复位期间引脚是高阻，无下拉时电机可能被干扰误动 → 硬件下拉 + STBY 保留跳线可强制使能
- **PB2 是 BOOT1，不能当普通 IO**（v3.0 新增）：复位期间 PB2 被拉高 → MCU 从 **SRAM** 启动而不是 Flash → 现象是"上电固件不跑"（用调试器又能跑）→ 本项目把 PB2 标为**保留勿接**（不能接按键、不能接复位时可能输出高电平的传感器）
- **TIM2 Full Remap 会与 USART2 抢 PA2/PA3**（v3.0 新增）：Full Remap 把 TIM2_CH3/CH4 复用到 PA2/PA3，而 PA2/PA3 同时是 USART2 默认脚 → 本项目**不用 TIM2**（保持默认映射），编码器改用 TIM4+TIM3
- **PA11 只能作输出**（原 USB DM）：拿来做 PWM 输出正好，**不能拿来做输入**
- **看引脚不能只看"能不能用"，还要看"复位期间它是什么电平"**：BOOT0/BOOT1、JTAG 脚、USB 脚都属于这类雷区

### OLED 中英文显示 · 2026-09-23 实测

**① 中文字库必须"子集化"，不能整库进 Flash**
一个完整中文字库几 MB，而 STM32F103C8T6 只有 **64KB Flash**（当时固件已用 ~30KB）。
做法：`tools/生成字库.py` 用 **PIL + simhei.ttf** 把**用到的字**渲染成 16×16 点阵，输出 `font_subset.h`。
实测：**ASCII 95 字（570B）+ 汉字 38 字（1216B）≈ 1.9KB**，完全放得下。

**② 新增汉字忘加进字表的坑（做了自动报警）**
现象：屏幕上那个字画成**空心方框**，或者干脆空白，很难定位。
应对：`Ol_Text()` 查不到字模时**画空心方框 + 串口打印** `# 字库缺字：UTF-8 xx xx xx → 请加进 CN_CHARS`。
流程：**改 `tools/生成字库.py` 的 CN_CHARS → 重跑脚本 → 重新编译**，三步缺一不可。

**③ 字模生成的阈值很关键**
PIL 渲染后要二值化：阈值太高（如 200）→ 笔画细的字**缺笔画**；太低（如 50）→ **糊成一团**。
实测 **阈值 110** 对 16×16 黑体效果好；ASCII 用 consola.ttf 渲染到 6×8 会略毛糙（可读，但不如真位图字模锐利）。

**④ 汉字占 2 页，画的时候要同时改 page 和 page+1**
SSD1306 是页寻址（每页 8 行）：16×16 汉字跨 **2 页**，`fb[page]` 放上半 8 行、`fb[page+1]` 放下半 8 行。
只写一页 → 汉字只显示上半截（这个现象很有迷惑性，容易误判成"字模坏了"）。

**⑤ 先建帧缓冲再一次性刷屏**
不要在循环里逐字发 I2C（100 个字符 = 100 次传输，又慢又容易半屏）。用 `s_fb[8][128]` 画完再 `Ol_FbFlush()`。

**⑥ 实测结论**：`OLEDTXT` 测试页四行（ASCII 符号行 / 中文显示测试 / 状态速度偏差左右 / 英文长串）**一次成功，零缺字**。

### OLED（0.96" SSD1306）· 2026-09-23 实测

**① 型号/地址/上拉全靠"拍背面丝印"确认**
背面丝印 `0.96 OLED` + `IIC ADRESS SELECT 0x78` + `R5/R6/R7/R10 = 472`：
→ **SSD1306**（0.96"+I2C 基本都是它；SH1106 多为 1.3"）、**7bit 地址 0x3C**、**板载已有 4.7k 上拉**。
不用猜、也不用另加电阻。

**② 板载上拉是拉到 VCC 的 → 所以 VCC 必须是 3.3V**
这条是本元件最容易犯的错：若图方便接 5V，OLED 自己的 4.7k 就把**整条 I2C2 拉到 5V**；
现在只有 OLED 时看不出问题，但将来挂上 **MPU6050（3.3V 器件，SDA/SCL 极限约 VDD+0.3=3.6V）就会被 5V 打坏**。
→ **OLED VCC 一律接 3V3**（顺带 I2C2 也是 3.3V 总线，与规划一致）。

**③ 两条 I2C 总线绝不能混**
I2C1（PB8/PB9，上拉 **5V**）只挂灰度；I2C2（PB10/PB11，上拉 **3.3V**）挂 OLED/MPU6050。
把 OLED 插到灰度那条 16P 座上 = **5V 打坏 SSD1306**。

**④ 0.96" 有"上黄下蓝"双色面板，不是花屏**
面板上 16 行黄色、下 48 行蓝色是**屏体类型**，不是驱动问题。测试图案在上半屏显示为黄色属正常。

**⑤ bring-up 用棋盘格比点亮全屏更有信息量**
棋盘格 + 四周边框能同时检验**行/页寻址、列扫描、每点独立控制**；
"全屏点亮"只能证明供电和电荷泵正常，暴露不出寻址错误。

**⑥ 排查口诀**：先 `OLSCAN`（只探地址）再 `OLED`（初始化+图案）。
地址不应答 = 总线层问题；应答了但屏不对 = 初始化参数/驱动型号问题。

### 超声波（HC-SR04）· 2026-09-23 实测（面包板 bring-up）

**① 命令处理写在串口中断里 → 输出会被静默丢掉**
现象：`US` 调试命令的回复时有时无；有时只跑一半。
原因：中断里的 `printf` 和主循环的 `printf` 抢同一个 UART，`HAL_UART_Transmit` 返回 BUSY，输出直接丢弃；而且命令里的 `HAL_Delay` 还把中断给堵住了。
应对：**中断里只收行，命令执行放到主循环**（`Tlm_Poll()`）。这也顺手把“阻塞几十毫秒的中断”这个隐患一并去掉了。

**② 两个触发源各测各的 → 撞出假的“超量程”**
现象：`$U` 里出现大量 `width=30002µs`（正好卡在 30ms 超时）→ 判为 −2 “没回波”；但同一颗探头单独测却是 100%。
原因：主循环每 100ms 测一颗、`US` 命令又自己测一轮 → **同一颗模块被过密触发**；HC-SR04 被短间隔重触发时 Echo 会拖成一条长高电平。
应对：**把节拍守则放到驱动层**（`Us_Read()` 内部判断距上次触发是否够 60ms，不够就返回 `-6` 并不真触发）——不管谁来调都不会撞。

**③ 测量失败后继续密集重触发 → 模块把自己锁死**
现象：某颗一旦开始报 −2，就会连续报下去；而且这个“卡死”状态会在两颗之间游走（上一轮左好右坏，下一轮反过来）。
原因：HC-SR04 在“没回波”时会输约 200ms 长高电平；在这段时间里继续触发，它就缓不过来。
应对：**失败后把该颗的恢复间隔拉到 600ms**（`US_RECOVER_MS`，成功时只需 60ms）——实测能把卡死状态自动解开，恢复 100%。

**④ 探头离反射面 < 20cm 时不可靠（关键物理规律，与代码无关）**
实测规律：**≥ 20cm 的所有读数都是 100%；< 20cm 就掉到 37~58%**。
原因：发射后振子还在余振，16cm 的回波只用 ~0.96ms 就回来了，落在余振里分不出来 → 报 −2。数据手册写“2cm 起”，但**廉价模块实际可靠下限普遍在 20~30cm**。
应对：**安装高度/前置距离按 ≥ 25~30cm 设计**（赛车避障本来就在 30cm 以上才有意义）。

**⑤ 波束角只有 ~15°，歪 10° 就整个打偏**
现象：手握两颗时，一颗读 206mm、另一颗读 575mm；转正后两者立刻变成 322/332mm（一致）。
应对：探头必须**平行正对**同一反射面；调试时不要手持（手抖 + 歪角），把探头垫高放稳、用手拿反射物。

**⑥ 杜邦线掉一根就变 “完全无反应”**
现象：左探头从“偶尔测不到”变成 100% 报 −1（触发后 Echo 从头到尾没动过）。
原因：**GND 杜邦线从面包板里脱出来**（就是本项目早就记过的“杜邦线靠摩擦接触”那个坑）。
应对：`-1` 优先查线（Trig / Echo / VCC / GND 四根都按一下），不要先怀疑代码或模块。

### BLE 蓝牙模块 · 2026-09-30 排查记录（**未验收，挂起**）

**① 模块身份（手机 BLE App 截图确认）**
名称 `HC-06`，但暴露的是 **BLE GATT 服务 `FFE0`**（`FFE1` Write&Notify、`FFE2` Write）→ **不是经典蓝牙 SPP**。
→ 这解释了"iOS 设置里能连上却收发不了数据"：**iOS 不支持经典 SPP，而这个模块走 BLE GATT**。

**② BLE App 必须"订阅 Notify"才能收到数据（最容易漏的一步）**
只"连接"不订阅 → 永远看不到模块发来的东西。要在 `FFE1` 里打开 **Notify/通知** 开关。
（用户实测：开 Notify 前只看到自己 Write 的日志，没有任何接收记录）

**③ 现象：手机 Write 显示成功，但车端收不到；车端发的手机也收不到 → 双向不通**
关键点：**BLE 层的 Write 成功 ≠ 串口数据送达** —— GATT 只会 ACK"写"这个动作，
模块是否把字节吐到 TXD 引脚、波特率对不对，都在这层之外。
排查已试：USART2 波特率 115200、9600 都试过，均未通。

**④ 下一步的决定性实验（已备好工具，未执行）**
固件里已加两个命令（`drv` 层无需改动）：
- `BTBAUD <n>`：运行时改 USART2 波特率
- `BTAT`：以当前波特率发 `AT`，并把模块回的字节打出来
→ **逐个试 4800/9600/19200/38400/57600/115200，回 `OK` 的那个就是模块真实波特率**
（HC-06 / AT-09 类模块默认 9600，也有部分默认 115200；这是"双向不通"概率最高的原因）

**⑤ 也别忘了最朴素的两条**
- **TXD/RXD 必须交叉接**（模块 TXD→PA3、RXD→PA2）；接成一对一会两个输出对顶 → **发热**（本次已发生过一次）
- **VCC 电压**：HC-06 类 3.6~6V（用 5V）；裸 3.3V BLE 型用 3V3。拿不准先 3V3

**⑥ 定位（决策 E-05）**：BLE **仅调试用、比赛不接** → **非关键路径**。
有线遥测（USB-TTL/USART1）已冻结并跑通，调试数据不受影响 → **不要为它耽误关键路径**。

### MPU6050 · 2026-09-23 实测

**① 和 OLED 共用 I2C2 是零成本的**
I2C 是总线协议，地址不同即可共存（OLED `0x3C` + MPU `0x68`）；两条线现成、上拉现成（OLED 板载 4.7k）。
→ 这也是「别急着删它」的核心理由：**它不占任何额外引脚，只占一个 4P 座**。

**② VCC 必须 3.3V（和 OLED 同一条总线，别混电压）**
MPU6050 的 SDA/SCL 极限约 VDD+0.3=3.6V；而 **I2C1（灰度）是 5V 上拉总线** → 把 MPU 挂上去会被打坏（同理 OLED）。

**③ 验证加速度计对不对，最快的判据是「模长≈1g」**
静止时 `√(ax²+ay²+az²)` 应 ≈ **1.0 g**（实测 1.04 g ✓）。
这比「看数值有没有变化」强得多 —— 它同时验证了量程配置、符号、换算系数、读取顺序都对。

**④ 陀螺仪静止也有零偏，用之前必须标定**
实测静止时 x 轴有 −2~−5 dps 的漂动。这不是坏，是 MPU6050 的常态：
真要用角速度，第一步是**静置采几百个样本取均值当零偏**，之后读数都要减掉它。

**⑤ 定位（决策 E-24）：它是诊断仪器，不是控制输入**
循迹车的基本信息是「线在哪」（八路灰度给），陀螺仪的航向是冗余的；
它真正的价值是**看振动／加减速冲击／碰撞尖峰**，以及 PID 调参时区分「传感器噪声 vs 转向过冲」。
→ 硬件保留座子、软件优先级最低；遇到「找不到原因的抖动／振荡」时再插上诊断。

### 按键 / 蜂鸣器 · 2026-09-23 实测

**① 四脚轻触开关是"两两连通"的 —— 插错脚会永远不动作（本次实际踩到）**
现象：按住按键，固件读到的还是"松开"；换面包板孔位后立刻正常。
原因：4 脚轻触开关**同一侧的两个脚内部本来就短接**，把线插在同一侧 = 开关永远不参与通断。
应对：**用对角线的两个脚**（或跨到另一侧）。**秒判**：万用表通断档量两个脚 —— 不按不通、按下通才对。
（本次最终原因就是面包板插错孔，不是代码/引脚问题）

**② 按键状态要"两个状态都确认"才算验完**
只测到"按下"不够：还要确认**松开时能回到另一个电平**。
本机实测：松开 `PA12=1`（核心板 1.5k 上拉 + 内部上拉）、按下 `PA12=0` → 两个状态都对才收工。

**③ 蜂鸣器绝不能直接挂 GPIO**
有源蜂鸣器 20~30mA，超 STM32 单脚能力；且感性负载断电有反电动势。
正确：`PB15 → 1k → NPN(S8050) 基极`，发射极→GND，集电极→蜂鸣器负极，蜂鸣器正极→3V3，**两端并续流二极管**。
高电平 = 三极管导通 = 响。

**④ 排查顺序（本次证明有效的三步）**：先 `KEY` 读电平（不动）→ 再用万用表量 PA12 对 GND（松开 3.3V / 按下 0V）→ 最后查物理接插件。
**"读数不变"先怀疑接插件**（面包板孔位/杜邦线/开关脚位），这条在本项目已经连续命中三次（灰度 GND、编码器插错排针、按键错孔）。

### 编码器（JGB37-520 自带，硬件编码器模式）· 2026-09-23 实测

**① `TIM_Encoder_InitTypeDef` 用 `{0}` 初始化 → 计数自己狂跑（最坑的一条）**
现象：两路计数每 0.5 秒自己涨几千，看起来像"输入悬空拾噪"或"编码器在转"。
原因：`{0}` 让 `EncoderMode = 0`，而合法值只有 `TI1`(1) / `TI2`(2) / `TI12`(3)；
**模式为 0 = 从模式关闭 → 定时器退回用内部 64MHz 时钟计数**，16 位计数器每秒回绕上千次。
应对：**必须显式写 `enc.EncoderMode = TIM_ENCODERMODE_TI12;`**（两通道都计，4 倍频）。
教训：HAL 的结构体初始化里，**"0 有语义"的字段不能靠 memset 蒙**。

**② 判断"是噪声还是真在动"→ 先看静止基线**
连读 3 次静止值：`Δ = 0` 才说明输入干净；若静止就漂 → 查 VCC/A-B 是否悬空。
本次两路静止都是 0 → 之前看到的"漂移"其实是人手在转轮子，不是噪声。

**③ C1/C2 反接只影响符号，不用重新接线**
A/B 是正交两相，交换只是把相位反过来：**计数照样准、不丢数、每圈计数一样**，只有**正负方向相反**。
应对：用软件集中修正（`ENC_SIGN_L/R`、`MOT_SIGN_L/R` 宏），**不动机器、不动线**（减少接触不良的机会）。
符号的正式对齐放在**电机能通电转的那次**做（那时才知道"哪个方向算前进"）。

**④ "物理轮子 ↔ 逻辑通道"怎么定？→ 转一个轮子看哪路在动**
本次踩到：新电机编码器**还插在 PB6/PB7**（老通道）→ 表现为"转新轮子，动的却是 L"。
排查范式：清零 → 静止确认基线 → 只转一个轮子 → 看哪路在动 → 就能把映射关系钉死。

**⑤ 验收结论**：两路都通过（左 TIM4/PB6·PB7、右 TIM3/PA6·PA7），
手转增量均匀（每次 ~200 counts / 0.45s ≈ 460 counts/s ≈ 20 RPM 手速），
转一路时另一路稳定为 0 → **两路独立、零丢数**。

### 灰度（感为八路 I²C）· 2026-09-23 实测

**① `KEY` 不是板上实体按键，是一个输入引脚**
现象：想在板上找按键却只看到“母头”。
应对：**用杜邦线短接 16P 的针 3（KEY）↔ 针 1（GND）** 代替按下；
短接~0.2s = 短按，保持~4s = 长按。
校准关键：**长按只是“进校准模式”，本身不记录**；之后要分别在黑场、白场各**短按**一次，**灯灭 = 校准完成**。

**② I²C 上拉必须是 5V —— 面包板上最容易搞错的一条**
现象：ping 永远 FAIL，但模块 LEDs 亮着（供电正常）。
原因：面包板上没有上拉；或误以为“3.3V 器件就用 3.3V 上拉”。
应对：**插上模块板载的「SCL上拉 / SDA上拉」跳帽**（板载 5V/10k）——手册要求外置上拉源 **≥72% 供电电压 = 3.6V**，
3.3V 不达标；且**一条总线只能有一处上拉源**。PB8/PB9 是 FT 脚，允许 5V 上拉。

**③ 地址跳线会改地址**
插 AD0/AD1 会把 7bit 地址从 **0x4C** 变成 0x4D~0x4F（驱动就是按 0x4C 写的）。
调不通时先跑总线扇描（`GRSCAN`）：**一个都不应答 = 总线层没通；应答 0x4C = 一切就绪**。

**④ `ana` 全 0 + `dir` 全 0 = “没照到东西”，不是校准坏了**
模拟量是**物理测量**（不受校准影响）：全 0 只说明探头悬空/离面太远。
手册检测高度 **4~100mm，典型 20mm**。判据：贴着白面包板扫时 `ana` 应有 **50~100 counts** 的摆幅（实测 18~134）。

**⑤ 数字判定必须和模拟量交叉验证才算调通**
只看 `dir` 分档不够（可能是校准门限凑出来的）。**强证据**：判“黑”的那几路，`ana` 也正好是最高的那几路；
扫面包板时各通道按 **6→5→3→7→1** 依次起伏 → 证明**物理顺序、灵敏度、独立性全对**。

**⑥ 校准后不得改变安装高度；但装车/赛前必须重校**
手册原文：每次更改安装高度都应重新校准，且传感器对距离敏感。断电不丢记忆（不用每次上电重校）。
→ 面包板上校的准只是“面包板工况”的；**装到车上（高度/角度变了）、以及比赛现场（光照、胶带材质变了）都要重新校准**。

### 超声波 · 2026-09-30 成车（PCB）实测新增

**⑨ `-2`（超量程/无回波）在赛道上就是「前方空旷」，不是故障 —— A02 必读**
成车实测：两颗探头都完好时，**对着空气 → 100% 报 `-2`**；转过去对着物体 → 立刻 100% 正常。
- 赛道上**没有障碍物**时，超声波会**一直报 `-2`** —— **这是常态，不是坏**
- 真正的故障码是 **`-1`（`US_NO_RISE`，Echo 完全没动静 = 线掉/没供电/接错脚）**
- 驱动把 Echo 配成**输入+下拉**是故意的：掉线会稳定读到低电平 → 报 `-1`。
  所以**报 `-2` 说明 Echo 确实拉高了 = 线是通的、模块也响应了** —— 这个差别是本次定位问题的关键工具
- ⚠️ A02 的避障逻辑必须把 `mm <= 0` 当「很远」，**绝不能因为 `-2` 就停车或报警**

**⑩ 排查时「交换模块」会把「位置/朝向」一起换掉 → 归因会被混淆**
本次踩的坑：右超声波一直 `-2`，我把两颗模块对调后发现结果「跟着座位走」（右座仍坏），
于是判断「PCB 右通路有问题」。**但这个结论是错的** —— 对调时模块**连同它的物理位置和朝向**一起换了，
所以结果既可能是「座位坏」、也可能是「右边那个位置的朝向不好」，**两者根本没被分开**。
最后是让用户**只改朝向**（右边对着物体、左边对着空气）→ 结果立刻翻转 → 才真正锁定是**朝向问题**。

> **通用教训**：做 A/B 对调实验前，先想清楚这次交换**同时改变了哪些变量**。
> 一次只动一个变量；动不了的（如位置），就换一个**外部条件**（换个反射面）来把变量分离出来。

### 灰度极性与高度 · 2026-09-30 成车实测新增

**⑪ 黑白极性定案：`黑 = 0`、`白 = 1`（旧的「黑=1」记录是错的）**
实测（`dir` 打印顺序是**第8路 → 第1路**，最右边是第 1 路）：

| 动作 | 被遮通道 `ana` | 该位 `dir` |
|---|---|---|
| 只遮第 8 路 | 111 → 17 | 1 → 0 |
| 只遮第 1 路 | 87 → 13 | 1 → 0 |
| 盖住全部 8 路 | 87~128 → 1~25 | 全 1 → 全 0 |

⇒ 与**手册 §2.4**（接近黑 → 输出低电平）一致 ✓ 面包板那次「黑=1」记反了。
**两套极性要分清**：驱动原样返回（1=白/0=黑）；`$T` 帧与算法用手的是 **1=黑**（`app_trace.c` 归一化）。

**⑫ 顺带修掉的驱动 bug：旧版用「返回 0xFF」表示读失败**
但实测 **8 路全白时读数本身就是 0xFF**（车在白底上是最常见状态）→ 任何「== 0xFF 判失败」的代码都会误判。
已改为 `uint8_t Gr_ReadDigital(uint8_t *out)`：**返回 1=成功 / 0=失败**，读数和成功标志彻底分开。

**⑬ 高度一变，`dir` 会「悄悄乱判」，而且不报错 —— 这是最危险的一种失效**
监控刚开始那 40 秒（传感器不在校准高度上）的记录：
```
dir = 01001100   ana = [29 49 33 26 44 35 31 43]
```
判 1 的是第 7/4/3 路，但**模拟量最高的却是第 2/5/8 路** —— 数字判定与模拟量**对不上** ⇒
整体 `ana` 偏低（离面太远）时，门限会随机命中。
- **症状**：不报错、不报警，但 `dir` 和 `ana` 的排序矛盾
- **判据**：**永远要拿 `ana` 交叉验证 `dir`**（只看 `dir` 会被骗）
- **对策**：装车高度必须固定；每次改高度都重校；上赛道前在真实地面重校

### 供电 · 2026-09-30 成车实测新增（★ 最容易骗人的一条）

**⑭ 「只接 ST-Link 3V3」会让 5V_BUS 出现 ~3V 的虚压 —— 5V 域元件其实在 3V 下工作**

**现象**：整板只接了 ST-Link 的 3V3（没接 USB、没接 12V、MP1584 也不通），
但灰度和超声波**全部正常工作**，让人以为"没接 5V 也没事"。
用万用表一量：**开发板 5V 脚 ≈ 3V**（不是 0V，也不是 5V）。
插上核心板 USB 后：5V 脚变 **5.0V**，**板上好几个指示灯明显变亮**。

**机制**：核心板上的 LDO（RT9193）**内部有寄生二极管（输出 → 输入）**，
所以从 **3V3 脚倒灌 3.3V**，会在 **5V 脚漏出 ≈3V**。链路是：

```
ST-Link 3V3 ──→ 3V3_LOGIC ──→ 核心板 3V3 脚 ──[LDO 寄生二极管]──→ 5V 脚 ──→ 5V_BUS
```

**危害（这才是关键）**：
- 灰度、超声波、编码器都在 **5V_BUS** 上 → 实际拿到的是 **~3V**
- **灰度是"LED 发光 + 接收反射光"原理，亮度随供电电压变** → 3V 下校准的门限在 5V 下会偏
  ⇒ **这次在 3V 下做的灰度校准全部作废，必须在真 5V 下重校**
- 超声波/编码器同理：**能跑，但量程/精度/输出幅度都是在非额定电压下测的**

**教训与对策**：
1. **验收任何"靠电压工作"的传感器前，先用万用表量它自己的电源脚**（不要假设"板子亮了就是 5V"）
2. **看到灯变亮/变暗，是电压变了的强提示**，值得立刻量电压
3. **台面调试的干净方案**：插核心板 USB 供 5V（USB 5V → 5V 脚 → 5V_BUS + RT9193 → 3V3_LOGIC），
   **同时拔掉 ST-Link 的 3V3**（否则两路 3.3V 并联顶牛），ST-Link 只留 `SWDIO/SWCLK/GND`
4. **USB 与 12V 绝不同时接**（两个 5V 源会一起灌 5V_BUS）
5. 顺带：**灯越亮 ≠ 越好**，但**同一块板"灯突然变亮"= 电压升高了**，是个廉价有效的探针

### 蓝牙模块 · 2026-09-30 最终定案（★ 丝印不可信）

**⑮ 模块丝印写 `HC-06-V3.0`，实质是「BLE 克隆」，不是正牌经典 HC-06**

| 判据 | 正牌 HC-06（手册）| 这块实物 |
|---|---|---|
| 芯片 | **CSR BC417** | **杰理 AC6925A**（音频 SoC）✗ |
| `AT+VERSION` | **`hc01.com2.0`**（手册的防伪判据）| **`hc06V2.3_le`** —— **`_le` = Low Energy** ✗ |
| Windows 枚举 | 经典蓝牙 → **生成 SPP COM 口** | **只有 `BTHLE`（低功耗）**，**一个 SPP 口都没有** ✗ |
| 服务结构 | SPP | GATT `FFE0` → `FFE1(Notify,Write)` + `FFE2(Write)` |
| `AT+ROLE` / `AT+PIN` | 支持（商家视频里的 `AT+ROLE=S`、`AT+PIN=1234`）| **无回包，不支持** ✗ |

再加一条逻辑铁证：**LightBlue 是 BLE 专用 App，看不见经典蓝牙设备** —— 能在 LightBlue 里看到它，
说明**它一定在广播 BLE** ✓

> ⚠️ **教训**：**丝印和设备名都不可信**，尤其廉价模块。判定要走「芯片型号 + `AT+VERSION` + 系统枚举方式」三件套。
> 另外：**商家视频演示的可能是另一个版本/另一个型号**，不能拿视频当实物规格。

**⑯ 该模块的 AT 指令必须用 `\r\n` 结尾（这是之前 AT 全程失败的真正原因）**
实测（USB-TTL 直连，9600）：

| 发什么 | 结果 |
|---|---|
| `AT`（无结尾）| 无回包 ✗ |
| `AT\r`（只 CR）| 无回包 ✗ |
| **`AT\r\n`** | **`OK`** ✓✓ |

**支持的指令（很少）**：`AT` → `OK` ｜ `AT+VERSION` → `hc06V2.3_le` ｜ `AT+BAUD` → `BAUD=9600` ｜
`AT+NAME<x>` → `OKsetname` ｜ `AT+DEFAULT` → `OK` ｜ `AT+RESET` → `+OK`
**不支持**：`AT+ROLE`、`AT+PIN`/`AT+PSWD`、`AT+RX`/`AT+ADDR`，以及 HM-10 那一套（`AT+IMME`/`AT+START`/`AT+CON`…）

**⑰ BLE 侧连接不稳（待观察）**
现象：Windows「连上约 5 秒就掉」；iOS LightBlue「点 subscribe 约 1 秒变回 unsubscribe（CCCD 回到 0）」。
两者是**同一根因**：**BLE 连接保持不住**。

若仍不稳 ⇒ 判定为**廉价克隆固件质量问题**，按 `决策 E-05` **正式挂起**，不再投入。

| 线 | 接反后 | 危害 |
|---|---|---|
| M1 ↔ M2 | 交换 | 无害（只是转向反）|
| C1 ↔ C2 | 交换 | 无害（只是计数符号反）|
| **VCC ↔ GND** | **交换** | ⚠️ **编码器电源反接**，可能损坏 |

**现象（很有辨识度）**：四路编码器引脚（PB6/PB7/PA6/PA7）**全部稳定读到高电平、一点不跳变**。
原因：固件把编码器引脚配成 **`GPIO_MODE_AF_INPUT` + `GPIO_PULLUP`** ⇒ **信号没接上就是"悬空被上拉 = 全高"** ✓
⇒ **判据：引脚全高且不跳 = 信号没到 MCU（接线/电源），不是定时器问题** ✓
（对比：如果引脚**在跳变**但计数不动，那才是定时器/配置问题）

**教训**：
1. **插 6P 前一定按丝印对针序**（`1=M1 2=GND 3=C2 4=C1 5=VCC 6=M2`）；杜邦线头插反了肉眼很难看出
2. 看到"所有相关引脚都钉在一个电平不动" → **先怀疑接线/悬空**，别急着改代码
3. 本项目为此专门加了 `ENCPIN` 命令（直接读 PB6/PB7/PA6/PA7 原始电平）——**排查编码器最快的工具** ✓

**⑲ 两路编码器验收结果与符号定案**
| | 引脚 | 计数率（手转）| 前进方向符号 | 宏 |
|---|---|---|---|---|
| 左 | PB6/PB7（TIM4）| ~960 /s | **正** ✓ | `ENC_SIGN_L = (+1)` |
| 右 | PA6/PA7（TIM3）| ~1050 /s | 负 → 翻正 | `ENC_SIGN_R = (−1)` |

**两路都是四态齐全（00/01/10/11 全出现）= 正交信号健康** ✓ **停止时数值稳定、零丢数** ✓
符号不一致时**只改宏、不动接线** —— 这正是 `决策 E-22` 的设计目的，本轮实测证明它有效 ✓

### 板载快照（黑匣子）· 2026-10-01 实现完成

**背景**：**跑车的时候插不了 USB-TTL**（线会拖车）⇒ 必须有"脱机记录、事后读取"的能力。
实现：**RAM 记录 + 内部 Flash 持久化**（`app/app_log.{c,h}`、`tools/snapshot.py`）

| 层 | 说明 |
|---|---|
| **RAM** | 1200 帧 × 8B = 9.6KB，100Hz ⇒ **约 12 秒**（10/1 由 1600 帧/16KB 调小，给固件腾空间）；**跑车过程中只写 RAM（零阻塞）** |
| **内部 Flash** | 最后 **10KB**（`0x0800D800`）；**停车时自动把 RAM 写进去** ⇒ **掉电不丢** ✓ |
| **恢复** | 上电时 `Log_LoadFlash()` 自动把 Flash 内容读回 RAM ⇒ `DUMP` 照常可用 ✓ |

**⑳ ⚠️ 坑 1：写 STM32F1 的 Flash 时，数据长度【必须是偶数】—— 奇数会静默丢最后 1 字节**
现象：存 Flash 后 `magic` ✓、`cnt` ✓、但**校验和永远对不上**，读回校验也失败。
原因：F1 的 Flash **只能按半字（2 字节）编程**：
```
347 帧 × 5 字节 = 1735 字节（奇数！）
nbytes/2 = 867 个半字 = 1734 字节 ⇒ 最后 1 个字节没写进去 ✗
⇒ 校验和必然对不上 ✓
```
**对策**：帧结构**补一个 pad 字节凑成 6 字节**，并加编译期断言
`_Static_assert(sizeof(LogFrame) == 6, ...)` ✓ **这类错误以后编译器会直接拦下来** ✓

**㉑ 坑 2：写 Flash 期间【必须关中断】**
F1 编程 Flash 时 CPU 会停住等 BSY；而 **USART1 接收中断、SysTick 的 ISR 代码就在 Flash 里** ⇒
不关中断时"取指"与"正在编程"打架，可能破坏写入。
⇒ `__disable_irq()` / `__enable_irq()` 包住擦写（约 0.5 秒；此时车已停，安全）✓
⇒ 注意：关中断期间 `HAL_GetTick()` 不走，所以 HAL 的 Flash 超时计数失效 ——
但 BSY 会很快清掉，正常路径不需要超时 ✓

**㉒ 快照的 `ms` 时基是「按 100Hz 推算」的，实测约 117Hz ⇒ 时间轴约压缩 15%**
影响：曲线的**形状/相位**没问题（调参看的就是形状）✓；**但绝对时间别太当真** ✗
以后要精确：可以在帧里加 1 字节 tick，或把推算频率按实测改 ✓

**㉓ 快照能跨「重新烧录固件」存活** ✓（验证过：烧完固件后 `SNAP?` 仍显示原来的帧数）
原因：OpenOCD 只擦写程序覆盖的页（固件 36KB ⇒ 擦到 `0x08008FFF` 就停），不碰保留区 `0x0800D800+` ✓

### 循迹调参 · 2026-10-01 实测（★ 死区与参数默认值）

### 快照升级与轨迹重建 · 2026-10-01

**㉖ 只存 pwm 重建不出轨迹，必须存左右轮【真实】增量**
pwm 是**命令值**；打滑、堵转、死区都看不出来 ⇒ 帧里加 `dL/dR`（已按 `ENC_SIGN` 翻正）后：

```
v = (vL + vR)/2      ⇒ 积分得走过的距离
ω = (vR − vL)/轮距    ⇒ 积分得车头朝向   ⇒ (x,y) 连起来 = 实际轨迹 = 轨道形状
```

| 工具 | 作用 | 注意 |
|---|---|---|
| `tools/snapshot.py` | DUMP → CSV → 出图 | 固件 2026-10-01 前的日志没有 `dL/dR`/`gz` 两列 |
| `tools/track.py` | 航位推算重建轨迹 | **`mm_per_count` 未标定时长度比例不准，但形状对**（先用 `DISTCAL` 标定）|
| 陀螺仪 `gz` | 与轮式里程计积分出的朝向**交叉验证**（打滑/碰撞一目了然）| 帧里是 2°/s/LSB（±254°/s）|

**㉗ 容量红线要“算”而不是“看百分比”**
实测：`firmware.bin` = **47.3KB / 48KB（余量 1.8KB）**；`bss` = **16.4KB / 20KB**（快照 RAM 占 12.8KB）。
⇒ 再加功能前先估容量；**PlatformIO 的百分比不会提醒你压进快照保留区** ⇒ 所以加了编译后守门脚本。

**㛛 改了帧长，别忘了打印/统计里写死的每帧字节数**
现象：快照帧从 5B 改成 8B 后，`SNAP?` 仍报 `RAM=8000B`（1600×5），与代码里的 12.8KB 对不上。
原因：`Log_Status()` 里容量是按常量 `LOG_MAX_FRAMES * 5u` 算的，改结构体时没一起改。
对策：容量一律用 `sizeof(LogFrame)` 算（现已改）——**凡是与结构体尺寸相关的数字，一律算出来、不要手写**。

**㉞ `%f` 打印浮点会拉进 ~9KB 库 —— 一个字符的便宜，占了 1/5 个快照区**
现象：固件 45.3KB（快照区只给 10KB 时，红线 54KB 看着还行，但本来能更小）。
用 `nm --size-sort` 看最大符号，前十名里一半是它拉进来的：

| 符号 | 大小 | 谁拉进来的 |
|---|---|---|
| `_dtoa_r` | **2920** | `printf("%f")` 的双→ ASCII 转换 |
| `__adddf3` / `__subdf3` / `__muldf3`（及 `__aeabi_d*` 别名）| **~1900** | 只要一次 `(double)` 运算就得整套双精度软浮点 |
| `_printf_float` | **1132** | 浮点 printf 本体 |

**对策**：自己拼定点字符串（`Bsp_FmtFix(dst,n,v,dec,plus)`，输出与 `%.*f` 一致），
并把 `platformio.ini` 里的 `-Wl,-u,_printf_float` **删掉**（它是“强制链接”，不删就白改）。

| 阶段 | 固件 | 说明 |
|---|---|---|
| 改前 | 47780 B | 全部用 `%f`/`%g` |
| 去掉 `sscanf` | 45368 B | 自写 `parse_int`/`parse_float`（−2412）|
| 再去掉 `%f`/`%g` + 强制链接标志 | **36068 B** | **再减 9300** ✓ |

**教训**：
1. **占用大户往往不是你的代码，而是库** —— 先 `nm --size-sort` 看前列符号，再动手优化；
2. **`-u`（强制链接）会把你“已经不用的库”继续绑在固件上** —— 改完用法记得同时删标志；
3. 输出格式没变（`$P` 仍是 `14.00,0.00,0.30`，`$T` 的 err 仍是 `0.0`）—— 改前先把全部命令输出存成基线，改完逐条比对（数字归一化后比结构），
   本项目 18 条命令里 **16 条完全同构**，剩下 2 条正是故意改的 Flash 地址。

### BLE 无线日志 · 2026-10-01 实测（★ 两块模块同一结论）

**㉟ 蓝牙"一直测不通"的真凶是固件 —— `Bsp_Uart2Init()` 从没被调用**
现象：`BT` / `BTAT` / `BTSEND` 全无反应，AT 永远无回包，被当成"模块坏了/丝印是克隆"。
原因：`main()` 里只调了 `Bsp_UartInit()`（USART1）而**漏了 `Bsp_Uart2Init()`** ⇒ USART2 从未初始化，
HAL 对未初始化句柄发数据只是**静默返回错误**（连 `HAL_UART_Receive_IT` 也白搭）。
修好之后：车 → BLE **立刻通了**。
**教训**：外设"通了没通"要拿**真实链路**验（本项目的 `BTAT` 回环测试就很好用）；
之前还因为 0x… 漏调用，把两块好模块都冤枉了（`决策 E-05` 的"挂起"因此需要复核）。

**㊱ 非阻塞发送队列的竞态：`HAL_UART_Transmit_IT` 返回 BUSY 时，字节已经被出队了**
现象：同步头空口上变成 `aa aa 55`（少一个字节），PC 端永远找不到完整同步头。
原因：`u2_kick()` 先出队、再调 `HAL_UART_Transmit_IT`；若此刻上一字节还在发（返回 BUSY），
那个字节就永久丢了。⇒ 加 `busy` 标志位 + 失败时把字节**退回队列**。
**教训**：环形队列 + 中断发送要"**成功启动发送后才算出队**"。

**㊲ 流式解帧的顺序：对齐状态下**绝不能再**先找同步头**
现象（踩了两次）：每 25 帧只解出 1 帧、4 帧突发只解出 1 帧。
原因：主循环第一句就是 `find(SYNC)` → 一找到就把之前所有字节丢掉 ⇒ 把突发中间的合法帧全扔了。
正确顺序：**① 未对齐 → 找同步头；② 已对齐 → 先解帧；③ 解帧失败才回退重对齐**。
**教训**：解帧器要有"对齐状态"这个概念，别让"找头"常驻在主循环里。

**㊳ 这类廉价 BLE 克隆模块的吞吐天花板 ≈ 60~70 B/s（实测，两块模块一致）**

| 项 | JDY-69A-BLE | HC-06（老） |
|---|---|---|
| MTU | 248（波动）| 517 |
| 连接参数 | 可用 WinRT `ThroughputOptimized` 把 30ms/latency10 改成 **15ms/latency0** | 同 |
| 单次写入上限 | **~60 字节**（写 60B → 收到 62B ✓；写 120/200/300B → **整个丢弃** ✗）| 同 |
| 通知节拍 | **~1 条/s**（模块自己刷写节流）| 同 |
| **实测吞吐** | **66~68 B/s** | **65~68 B/s** |
| 固件侧丢弃 | **`drop=0`**（单片机把 290 B/s 全部推进了模块）| — |

**排查结论**：不是开发板（drop=0 + 数据逐字节完美）、不是 Windows、不是连接参数、不是波特率（9600，余量 3 倍）
⇒ **是模块固件的刷写节流**，AT 也改不了（且下行 TXD 未接）。
**对策**：字节率固定 ⇒ **帧越瘦、采样率越高**：8B → ~7.7 帧/s；4B → ~16 帧/s；2B → ~30 帧/s。
把无线当"实时看趋势"，100Hz 全精度交给板载快照。
**教训**：买 BLE 透传模块，**"一次能写多少字节"和"每秒能送几条"必须实测**，
别信"透传、最高 X kbps"的标称 —— 克隆模块的瓶颈在自己固件的刷写节拍上。

**㊴ 车 → BLE 通了，但 BLE → 车（下行）不通 —— 与模块 TXD 有关**
用 `PA2↔PA3` 短接做**回环测试**：能收到自己发的 `AT` ⇒ 单片机 RX、GPIO、NVIC、回调链全部正常；
但模块怎么都不回包（换模块也一样）⇒ 问题在**模块 TXD 那一根线/引脚**（或该方向没转发）。
回环测试是**切分"单片机侧 vs 模块侧"的一刀**，非常好用。

### BLE 帧的“时间含义” · 2026-10-01（★ 差点把标定算错 3 倍）

**㊷ 每帧 `dL/dR` 只是【10ms】的增量，但帧是【每 3 个采样才发 1 帧】—— 直接求和少 1/3**
代码事实（`app_log.c`）：`Log_Note()`（= 造一帧）由 `Trace_Step()` **每 10ms 调一次**；
而 `Log_BleTick()` 里 `if ((div = div + 1u) < 3u) { return; }` ⇒ **33.3Hz 才发一帧**，
**丢掉的那 2/3 不会补进下一帧** ⇒ 帧里的 `dL/dR` 永远是“上一个 10ms”的。
⇒ **用无线日志求和算里程/圈数，必须 ×3**（×3 后才等于 `ENC` 绝对计数差）。
**教训**：拿“增量型”数据求和前，先确认**采样率与发送率是否一致** —— 不一致就藏着比例因子。
> 同一天两次标定都稦在这上面：推车 Σ=1264、转轮子 Σ=3575 —— 都是“少 3 倍”的数字。

**㊸ mm/计数 至今没有定论（几组数据互相矛盾，不许当事实用）**

| 依据 | 反推 mm/计数 | 备注 |
|---|---|---|
| 100% 占空比 10506 计数/s ÷ 330RPM(5.5转/s) ⇒ 1910 计数/转，⌀70 轮 | **0.115** | 依赖“轮径 70”与“额定 330RPM”两个假设 |
| 推车“两张 A4 长边和 = 594mm” | 0.470（×3 修正后 ≈0.157）| 推车时轮子是否全程真在滚？未确认 |
| 手转“两次 5 圈”（目视计数）| ≈0.19（×3 修正后）| **“几圈”本身是目视估计，误差可能 2 倍** |

⇒ 三者不一致 ⇒ **至少有一处基准不可靠**（圈数估计？推车时轮子打滑/被抬？）
**对策（待做）**：在 BLE 流里**周期性附带编码器【绝对计数】的“锚帧”**（每 25 帧 +8B，≈5B/s），
之后“手转 N 圈”就能直接读绝对差 —— 不受丢帧/分成影响，一次测试就能定死。

### 工具与脚本 · 无线日志图形界面 · 2026-10-01

**㊹.1 陀螺仪字节是【有符号】的，当初解帧写成了无符号 ⇒ CSV 里的 gz 一直是错的**
固件里 `f->gz8 = (uint8_t)(int8_t)g`（存成 uint8 但语义是 int8），快照 DUMP 也按 `(int)(int8_t)` 打印；
而 `btlog.py` 的解帧写成了 `struct.unpack("<BbbbBbbB", ...)` —— **最后那个大写 B 是无符号** ✗。
后果：**负的 gz 变成 200 多**，再乘 2（`telemetry.py` 里 `gz = parts[16] * 2`）⇒ CSV 里出现 **510 °/s 这种假尖尖**（真实范围 ±254）。
修法：改成小写 `b`（`"<BbbbBbbb"`）—— 与固件/快照路径一致。
**教训**：二进制协议里“存成无符号但语义是有符号”是常见写法（C 里没别的选择），
解帧时**要按语义而不是按类型**取；本项目已有一份“打印时转 int8”的参照实现（`app_log.c` 的 DUMP）。
> 影响范围：`gz` 列（陀螺仪）—— `dl/dr/err/pwm/bits` 全部无误 ✓，
> 所以“靠 dl/dr 重建轨迹”的分析不受影响 ✓。

**㊺ 陀螺仪：现场已验正常 ✓，但两趟实车日志 gz 全 0 的原因**仍未完全确认
- ✓ **2026-10-01 下午现场验证**：手转整车 ⇒ 陀螺仪面板跟着跳、趋势条方向正确（用户确认“很准”）
- ✓ **已定案（同一晚）**：`1240`/`1257` 两趟 gz 全 0 = **芯片被复位回睡眠态**（见 ㊼）——
  不是排线问题，固件已加自愈；结论改为：**跑车前扫一眼面板确认在报数**（现在是“不报数它会自己叫醒并打印一行”）

**㊼ 陀螺仪突然“全 0”：MPU6050 被复位回上电默认，而固件只在开机初始化一次**
用户现象（2026-10-01 傍晚）：“更新之后陀螺仪数值消失了”，并提到**刚断过一次电、插上电充了一会儿**。

现场取证（这次车连着电脑，**直接读寄存器**）：
```
MPU> WHO_AM_I=0x68                    ← 在线 ✓
MPU> acc(g) 0.00 0.00 0.00 | gyro 0.0 0.0 0.0 | temp=36.5C   ← 数据全 0 ✗，但温度在更新
```
⇒ **芯片活着、I2C 通、温度在变，但加速度计/陀螺仪没在转换** —— 典型的 **PWR_MGMT_1 睡眠位=1**。
根因：`Mpu_Init()`（写 PWR_MGMT_1=0 唤醒）**只在开机调一次**；断电/上电时序一旦让它没醒成，
之后**再没人管**；而 `Mpu_Read()` 拿到的是一排 0，也不报错 ⇒ **陀螺仪静默失效**（日志里 gz 恒 0）。
> 这也解释了 ㊺ 里“12:40 / 12:57 两趟实车 gz 全 0”：那两次就是它睡着的时候 ✗

**修法（三件）**：
1. `Mpu_Read` **自愈**：连续 20 次读到“六轴全 0”（≈0.8 秒）就重新 `Mpu_Init()` 一次
   —— 判据很硬：**活着的加速度计静止时至少有一轴 ≈ ±1g，六轴全 0 物理上不可能**
2. `Mpu_Init` 加**回读确认**（写完 PWR_MGMT_1 读回来核 sleep 位），失败就打印明确报错
3. 命令：`MPUINIT`（手动重新初始化）、`MPURESET`（调试：复位回上电默认，用来验证自愈）

**⚠️ 测试教训（差点白验）**：我第一版验证命令写的是 `PWR_MGMT_1=0x40`（只置睡眠），
结果**数据一点没变**（仍是醒着时的值）⇒ 差点以为“自愈没生效”。真因是：
**MPU6050 睡眠时数据寄存器保留最后一次转换值，不会清零** ✗
⇒ 要复现用户那个故障，必须复现它的**确切状态**（上电默认 = `DEVICE_RESET 0x80`+`SLEEP 0x40`），
而不是一个“看起来差不多”的相似动作。改对之后，故意触发一次就验通了：
```
MPU6050 已复位回上电默认（回读 PWR_MGMT_1=0x40）
MPU6050 六轴全 0 OK 自动重新初始化（第 1 次）   ← 自愈叫了 ✓
MPU6050 init OK (WHO_AM_I=0x68)
```
**通用教训：验证“自愈/守门”类代码时，先想清楚“故障的确切状态是什么”，再构造它；
相似现象（例如置睡眠 vs 上电默认）可能根本走不到你的判据上。**

### 电机标定与 EMI · 2026-10-01 实测（★ 推翻昨晚的“死区”结论）

**㊵ 没开总电源 ⇒ TB6612 的 VM 没有 12V ⇒ 电机怎么都不转 —— 别误判成"死区"**
昨晚测出"占空比 5% 完全不动、10% 才起转"，写进了 ㉔ 的补充里；今早发现真因是
**车用总开关没开**，当时靠 TTL/ST-Link 的 5V/3V3 供电 —— 而**电机电源 VM 来自 12V 电池**。
真 12V 下重测：**5% 就转**（286 计数/s ≈ 22mm/s）。
**教训**：测电机前先确认 **12V_BUS 上电**（`MOT` 命令能改 CCR、能看方向真值表，但这些都与"电机有没有电"无关 ——
**只有编码器增量能证明它真转了**）。排查顺序：`ENCPIN`（信号）→ `ENC` 增量（真转）→ 再谈参数。

**㊶ 占空比 → 转速 标定（12V 电池、轮子架空、双轮同向，2026-10-01）**

|---|---|---|---|
| 5% | 286 | 287 | 22 mm/s |
| 8% | 572 | 599 | 45 |
| 10% | 766 | 818 | 61 |
| 15% | 1254 | 1346 | 99 |
| 20% | 1783 | 1892 | 140 |
| 30% | 2902 | 3004 | 226 |
| 50% | 5164 | 5184 | 395 |
| 80% | 8454 | 8494 | 647 |
| 100% | 10506 | 10726 | 811 |

\* 按 `track.py` 默认 `0.0764 mm/计数` 估算。**若**按"330RPM + ⌀70mm 轮"反推，真实值应约 **0.115 mm/计数**
（10506 计数/s × 0.115 ≈ 1210mm/s ✓ 与理论满速吻合）⇒ **建议用 `DISTCAL` 实测标定一次**，
否则 `track.py` 重建的轨迹长度会偏小约 1.5 倍。

### ★★★ 2026-10-01 早上的"车不听灰度、左右乱打舵" —— 真因是**模拟数据在驱动电机**

**㊸ 灰度判"在线"只在开机探一次 ⇒ 探不到就永远用模拟数据，而模拟数据【照样驱动电机】**
现象：长按 PA12 发车后，车**完全不理灰度**、左右轮交替猛加速（"左边快一下右边快一下"）；
长按 PA12 停车只是"稍微慢了一点"（因为它已经在丢线/精停之类的分支里）。
用户的猜测是"算法太灵敏/反转太大" —— **数据不支持这个猜测**。

**定位过程（可复用的排查法）**：
1. 无线日志 534 帧：`state` 全程 =1（循迹），灰度位图只有三种（`00011000`49% / `00001100`26% / `00110000`24%），
   **err 均值 0.06 但最大 |err| = 5.0**
2. **关键矛盾**：按公式 `err = sum/cnt − 3.5`，8 路传感器的**理论极限只有 ±3.5** ⇒ **±5.0 根本不可能是真数据**
3. 同时刻对比固件自己打的 ASCII `$T`：`0,0,0,0,1,1,0,0,3.6,...` —— **和二进制流一致**
   ⇒ 排除"PC 解码错"，问题在固件
4. 翻代码找到模拟分支：`e10 ∈ [−50,+50] → err = e10/10.0`（**±5.0 ✓**），
   而它伪造的位图正好是 `center,center+1` 两路黑、中心来回扫（**正好就是观察到的那三种 ✓**）
   ⇒ **那趟"跑车"全程是模拟数据**

**根因**：`Trace_Init()` 里 `s_online = Gr_Ping()` **只探一次**，而且**问得太早**：
实测 `$E,27,97,BOOT` ⇒ **固件开机 27ms 就探测完了**，而灰度模块**自己里面还有一颗 MCU**，
冷启动要几百毫秒才应答 ⇒ 冷启动（拧总开关）必然探不到，**永久**判离线。
更危险的是模拟数据**照样走完 PID 并驱动电机** ⇒ 车去追一条三角波"假线"（左右匀速扫）⇒ 表现为"不听灰度"。
（开机提示却写着"接上就自动走真实读数" —— 那是**假的**，以前根本不会重探。）

**归因修正（重要）**：一度以为是"TTL/ST-Link 的 5V 虚压导致模块没就绪"，
但用户全程用的是**车载总电源的真 5V** ⇒ **与供电无关**，就是"**问得太早 + 只问一次**"。
旁证：用**调试器复位**（烧录后复位，灰度模块一直有电）时能探到 ✓；**冷启动**（总开关）时探不到 ✗ ——
正好解释"昨天能跑、今天不行"。

**修复后冷启动实测（2026-10-01）**：
```
冷启动   # TRACE 灰度=不在线 驱动=关(只算不发)   ← 先判离线（正常）
+≤500ms  重探成功 → 切回真实读数 ✓
现在     # TRACE drive=0  灰度=在线 ；GR> ping=OK(0x66) ；$T 全白/pwm0/state0（真实数据路径）
```

**修复（2026-10-01）**：
1. 离线时**每 500ms 自动重探**（插好会自己切回真实读数，并打点 `$E 92 GRAY_ONLINE`）
2. **`allow_drive = 0`** —— 离线时**绝不允许驱动电机**（假数据永远不许开车），并 `Mo_Stop()`
3. 离线时打点 `$E 93 GRAY_OFFLINE` + 串口警告（第 1 次 + 每 5 秒一次，不刷屏）
4. **OLED 仪表盘显示 `NOGR`**（跑车时不用电脑也能一眼看出）
5. `TRACE 0|1` 回包带上灰度状态：`# TRACE drive=0  灰度=在线`
6. 开机提示改成真话："每 500ms 自动重探，插好会自己切回真实读数"

**教训**：
1. **"降级"路径绝不能有副作用**：模拟/兜底数据可以用于链路自检，但**不能驱动执行器**
2. **一次性的"在线探测"是定时炸弹**（尤其上电时序不确定的模块）⇒ 要么周期重探，要么用"用的时候再探"（`Gr_ReadDigital` 本来就返回成败）
3. **量纲能自证真伪**：`|err| > 3.5` 在 8 路传感器上物理不可能 —— 这种"不合理值"是抓假数据的最快线索
4. 别被现象带偏：用户以为是"调参/反转过大"，数据说是"根本没读到真数据"

### 工具与脚本 · 2026-10-01 新增

**㉘ Python 脚本在 Windows GBK 控制台下打印 Unicode 符号会直接崩**
现象：`python hardware/电气设计/自检.py` 跑到第 2 遍就 `UnicodeEncodeError: 'gbk' codec can't encode character '↔'`，
**自检直接中断，看起来像“脚本坏了”**（而实际第 1 遍全过）。
对策（两种都行，推荐两个都做）：
1. 脚本输出**只用 GBK 能编码的字符**（不要 emoji / “↔” / “⇒”）
2. 开头加一行兼底：`sys.stdout.reconfigure(errors="replace")` —— 不可编码的字符降级为 `?`，不影响判定与退出码
> 同类坑在本项目**已踩三次**（`firmware/check_size.py` 的注释里也写了同一条），
> **第三次是 agent 自己**：写监听脚本时用 `print('... ✓')` 到 GBK 控制台 ⇒ 脚本当场崩、还丢了关键日志。
> **铁律**：命令行小工具**也**要 `python -u` + 纯 ASCII 输出（或 `sys.stdout.reconfigure(errors="replace")`）。

**㉙ “实际赶过计划”后，文档会静默落后一整代**
PCB 提前 11 天到货、车 10/1 就跑通了，但 `firmware/README.md`、看板、接口文档还写着“未开始/待接/模拟数据”。
教训：**节点提前完成的那一刻就要同步文档**，否则下次看文档的人会按过时状态做决策。
（与 经验与踩坑 v1.30 ⑥“提前完成造成的假不一致”是同一类问题的两个方向）

**㉚ 编译后守门脚本“看着挂了，其实没触发”**
现象：`firmware/check_size.py` 里写的是 `env.AddPostAction("buildprog", check_size)`，
但 `pio run` 与 `pio run -t buildprog` **都不打印任何东西** —— 守门完全没生效，看起来却“已经加上了”。
原因：`AddPostAction` 要挂在**真实存在的构建节点**上；`"buildprog"` 这个目标名不在本次构建的依赖链里，动作就永远不会被调。
对策：挂到链接产物节点——
```python
env.AddPostAction("$BUILD_DIR/${PROGNAME}.bin", check_size)
```
⇒ 每次重新链接都会跑，实测输出 `[OK] size check: firmware.bin = 47324 bytes, 1828 bytes left (3.7% margin)`。
**教训：写了守门/检查脚本，一定要用“故意触发”的方式验证它真的会叫**（比如临时把阀值改小），
否则它只是个安慰剂。同类：`自检.py` 也是因为它真的崩了才被发现（见 ㉘）。

### 协作脚本 · 提交/拉取（提交流程）· 2026-10-01

**提醒页把人指向“先拉取” ⇒ 有未提交改动的人会白丢文件（已修）**

- 现象：`提交.bat` 的提醒页原本写「还没拉取 → 输入 N 退出，先双击『拉取.bat』」。而 `拉取.bat` 是 `reset --hard` + `clean -fd`（强制对齐云端）⇒ **没提交过的新文件会被直接删除，且在 git 里救不回来**（从未入库 ⇒ 无历史）。
- 正确处置（已写进脚本与《说明书》）：**手里有没提交的活 → 一律直接「提交」**；push 被拒时脚本会自动 `pull --no-edit` 合并再推，改动不会丢；**「拉取」只用于开工前（本地干净时）**。
- 通用原则：两个按钮的语义必须区分清楚——「提交」= 先保住我的活再合并别人；「拉取」= 丢掉我的活、变成云端的样子。凡是提示用户“操作失败请先拉取”的地方，都要先问一句“本地有没有没提交的活”。

### I²C 与供电（第 3 周新增，最容易烧器件）
- **灰度模块的板载上拉是 5V（10k）**（感为手册原文）→ 若把 3.3V 器件（SSD1306 OLED、MPU6050）挂到同一条总线上，**SDA/SCL 会被拉到 5V，超过它们约 3.6V 的极限，会烧** → 本项目把两条总线拆开：I2C1（灰度，5V 上拉）与 I2C2（OLED+MPU6050，3.3V 上拉）**绝不并联**
- **STM32F103 的 PB8/PB9 是 FT（5V 容忍）脚**，open-drain 模式下允许总线上拉到 5V → 跟 5V 传感器通信没问题；但**不可把 5V 上拉总线接到任何非 FT 脚**
- **一个 I²C 总线上只允许一处上拉源**：板载有上拉时 PCB 不要再并 3.3V 上拉，否则等效上拉变成高压侧，仍会打坏低压器件
- **专用电机排线里混着编码器信号**：JGB37-520 的 6 芯线同时走 M+/M−（2A 级、PWM 开关）与编码器 A/B/VCC/GND → 噪声耦合会丢计数；应对：A/B 串 100Ω + 并 1nF，编码器 VCC 就近 100nF，固件再做“最大跳变”过滤
- **电机侧连接器选型要注意额定电流**：JST-XH 触点约 3A，而 JGB37-520 堆转可到 2A+ → 堆转不要久留，否则座子发热
- **核心板自带 LDO（RT9193）与自备 LDO 不能同时对打**：5V 脚与 3V3 脚只能接一个；本项目只送 5V，3.3V 由核心板输出（≤300mA，需核算负载）

### 机械

### 工具与脚本
- **Windows 批处理（.bat）不能存成 UTF-8**：含中文的 UTF-8 .bat 会让 cmd 解析器错位（报「命令语法不正确」或把半行中文当命令执行）→ 必须存成 GBK 编码 + CRLF 换行
- **控制台代码页与 git 输出冲突**：git 输出是 UTF-8，中文 Windows 控制台默认 GBK（936），直接显示会让中文文件名/提交信息乱码 → 在 git 命令前后临时 `chcp 65001` / `chcp 936` 切换（脚本已内置）
- **用 `for /f` 抓取 git 配置时要先切 65001**：cmd 变量内部是 Unicode，抓取时按当时代码页解码；936 下抓 UTF-8 输出会导致中文被「双重转换」变成乱码（显示正常但内容是错的）
- **`git reset --hard` 会删掉“已 git add 但未提交”的新文件**（未 add 的 `??` 文件则会保留）→ 想做“只还原不删新文件”的工具，必须先在 reset 前执行 `git reset -q` 取消暂存
- **批处理文件的换行符必须统一成 CRLF**：混用（例如补丁只给新增部分写了 LF）会让 cmd 解析错位，报出一堆“xx 不是内部或外部命令”的碎片错误 → 每次改完 .bat 都要检查
- **测试 .bat 时注意两类假象**：①测试脚本若未提交，会被 `git clean -fd` 删掉导致 cmd 读串；②测试脚本若是“已修改的跟踪文件”，会被 `reset --hard` 中途还原导致同样问题 → 正确做法：把“输入已固定”的测试脚本提交并推送到沙盒远端，保证与远端一致
- **PlatformIO + stm32cube 框架（无 CubeMX 生成的 `it.c`）必须自己写 `SysTick_Handler`**：`HAL_Init()` 会开 SysTick 中断做毫秒计时，缺处理函数就跳进“默认处理器”的死循环——现象是 **LED 不闪、串口无输出、像死机**，但用调试器看会发现时钟/UART 寄存器都已正确初始化。排查捷径：`openocd` 里 `reg xpsr`，IPSR（低 9 位）= 15 即卡在 SysTick
- **读串口的脚本不要写 `while True: readline()`**：小车 100Hz 持续输出时永远读不完 → 用“限时循环”或设行数上限
- **PlatformIO 首次编译要联网**：会自动下载工具链与框架（约 200MB，国内需代理，5~15 分钟）；之后的增量编译只要几秒
- **`printf` 打印浮点要加链接参数** `-Wl,-u,_printf_float`（否则 `%f` 输出空或错乱）
- **HAL 的 `HAL_xxx_MspInit` 不能加 `static`**（HAL 头文件里是非静态声明，加了会编译报错）
- **自动化测试 `set /p` 的三个坑**：①**批量送入**（管道 / 重定向 / SendKeys 瞬时连发）会被 `set /p` 当“整行”读走，只有真实逐字键盘输入才按行读；②喂给重定向的输入文件**必须是 CRLF**，LF-only 会让第一行把后续内容全吃掉；③**`chcp 65001` 执行过后，重定向 stdin 下的 `set /p` 一律读到空**（真实控制台键盘输入不受影响）→ 测试交互脚本时先用无 `chcp` 的逻辑副本验证分支，再用真实控制台冒烟
- **`.bat` 里中文 `echo` 不能放在 `chcp 65001` 与 `chcp 936` 之间**：脚本本身是 GBK，控制台处于 UTF-8 时会显示成乱码 → 只让 git 输出留在 65001 段内，中文提示一律放在段外
- **“拉取并提交”合在一个脚本里是设计缺陷**（2026-09-13 修正）：它诱导“先改再拉”，一旦别人也改了同一处就会撞车 → 拆成「拉取.bat」（开工前）+「提交.bat」（收工时），顺序直接由脚本名固定下来；并把“已拉取？”做成 `提交.bat` 里的确认页（拉取 → 放入 → 提交），把提醒做进流程而不是只写在文档里
- **ChatGPT 的 GitHub 连接器是“用户级授权”，协作者也能读**（2026-09-13 实测）：一度以为“只有仓库所有者能用”——那是 GitHub App **安装**的规则（只能装到自己名下的账号）；这个连接器不走安装，GitHub 侧显示在 `Settings → Applications → Authorized GitHub Apps` 里的 `ChatGPT Codex Connector`（Owned by openai），而 `Installed GitHub Apps` 里是空的 → 访问范围 = **你自己 GitHub 账号对仓库的权限**，所以仓库协作者在自己的 ChatGPT 里连接自己的账号即可读。坑点：一直在找“选仓库 / Configure”是白找
- **测试建议**：脚本改动后用「固定值替换输入」的方式在沙盒仓库（裸仓库 + 克隆）里跑完整流程，比真实键盘更可控
- **LaTeX `standalone` 类在 xelatex 下不会自动裁边**：页面仍是 letter 尺寸，**长图会被截掉尾部**（本项目第一版接线图就丢了最后一栏）→ 用 `preview` 宏包（`\usepackage[active,tightpage]{preview}` + `\PreviewEnvironment{circuitikz}`）把页面设成内容尺寸；但 **`preview` 与 `standalone` 同时加载会产出 15 字节的空 PDF**，两个只能留一个
- **xelatex 输出中文要 xeCJK + 系统字体**（`\setCJKmainfont{Microsoft YaHei}`）；编译必须在 **ASCII 路径**的临时目录里做（中文路径下 pdftoppm / pdftotext 不稳，PowerShell 脚本也会被 cp936 误读）→ `hardware/电气设计/生成接线图.py` 就是这么做的
- **circuitikz 的 `node[pmos]` 默认是竖放的**，旋转后锚点跟着转，直接接 `(Q1.D)/(Q1.S)` 会接出一团乱线 → 评审图里改用「模块框 + 文字」表示未定器件
- **画原理图前先给版面定约定再落坐标**：本项目电源图把 12V/5V/3.3V/接地四条母线各占一条 y，并规定「12V 支路下拉全部落在 x ≤ 16.6、5V 支路落在 x ∈ [22,24]」，于是全图可证不相交——比事后靠肉眼找交叉省事得多

### 工具与协作 · 2026-09-30 新增

1. **`.bat` 必须存成 GBK + CRLF**（`chcp 936`）—— 否则中文全乱码。
   新建 `.bat` 时用 `open(p,'wb').write(text.replace('\n','\r\n').encode('gbk'))`，
   别用 UTF-8 写。同理 **PowerShell 5 读 `.ps1` 也按 GBK 解码**，脚本里写中文会直接解析报错
   → 跨工具脚本**要么统一 GBK，要么纯 ASCII**。
2. **`.vscode/launch.json` 与 `c_cpp_properties.json` 含本机绝对路径**（带 Windows 用户名）
   → **不能提交**：队友机器上失效、还泄露路径。
   `.gitignore` 要写 `.vscode/*` + `!.vscode/{settings,tasks,extensions}.json`
   （只共享这三个"公共配置"）。注意：**父目录被整体排除时，嵌套 `.gitignore` 无法再放行**，
   所以不能用 `.vscode/` 这种写法。
3. **PlatformIO 的 `include/` 是默认约定**：目录不存在时 VS Code"问题"面板会报两条黄三角
   （`无法找到 .../include`）。**不影响编译/烧录/调试**，但会让小白误以为出错 →
   放一个 `firmware/include/README.md` 占位即可（本工程头文件与源文件同目录，不用 `include/`）。
4. **两个模块同时发同一帧会双倍帧率**：循迹（100Hz）和避障（2Hz）都发 `$T` 会污染日志。
   解法：**只有循迹发 `$T`**，避障用 `$E` 事件打点；仲裁放 `main.c`，用"接管标志"让循迹停发。
5. **"只算不发"是最好的安全默认值**：算法骨架出厂默认不驱动电机，
   但要**仍然输出 `$T`**（报"打算给多少 PWM"）—— 这样上车前就能干看算法对不对，
   既防窜车又不牺牲可观测性。
6. **规划文档与实际提前完成会产生"假不一致"**：引脚表计划 9/28 冻结、实际 9/23 就冻了，
   结果 `自检.py` 报 FAIL。**遇到这类报警先判断是"真错"还是"提前完成"**，
   提前完成就同步计划类文档 + 修正检查规则，**不要为了过检查去改事实**。
